### ② 后端自动双向改写「本机地址」—— 不用再改 `/etc/hosts`

`host.docker.internal` 是**容器里**访问宿主用的名字; 裸机后端跑在宿主上, 那个名字
从宿主侧连不通(解析到 Docker 虚拟网卡 198.18.x.x, TCP 能连上但没有服务应答)。

以前只有一条路: `sudo tmctl.sh local hosts fix`(改宿主 `/etc/hosts`, 要 root)。
现在后端按"自己跑在哪"自动改写:

| 后端在哪 | 填 `127.0.0.1` / `localhost` | 填 `host.docker.internal` |
|---|---|---|
| 容器里 | → `host.docker.internal` | 原样 |
| 宿主上 | 原样 | → `127.0.0.1` |

- HTTP: `backend_gateway/app/core/settings_store.py` 的 `_rewrite_loopback`
- git 远端(SSH): `backend_gateway/app/core/git_sync.py` 的 `_rewrite_remote`(新增)

**同一个设置值在两种部署模式下都通** —— 切模式不用改设置, 也不用改 hosts。
`local hosts check/fix` 保留着, 只给"别的工具(curl/ssh)也要用这个别名"用。

### ③ 修掉一个让"全新部署起不来"的真 bug

`init_db()` 的 stamp 兜底把"版本表不存在"一律当成"老环境用 create_all 建的",
于是**全新空库**被 stamp 到 head —— 版本号是 head 但**一张表都没建**,
后端报 `Table 'testmate.agents' doesn't exist`, 而 alembic 说"已是最新"。

而且迁移链本身**不能从零跑**: `0001_initial` 建的是远古 agents 表, `0003` 去
`ALTER` 一个**从没被迁移建过**的列 (`category`) —— 0001~0022 是"补丁叠在 create_all
之上"的, 前提是库已经建好了。

现在按"库里有没有业务表"分流: 没有 → 用模型建出当前完整 schema (`create_all`) +
`stamp head`; 有 → 照旧按版本号 `upgrade`。

### ⑥ 登录页改成"免密优先"—— 要密码的账号才摆密码框

**改之前**: 登录页默认只有一个用户名框 + 一句「用密码登录」。用户填完账号点登录,
后端才回 `password_required` → 前端这才展开密码框。**白挨一次失败**, 而且那一次
失败还会被登录限流计数 (10 次 / 15 分钟)。

**改之后**: 登录页**先问后端这个账号要不要密码**, 再决定摆不摆密码框。

- 新增公开端点 `GET /api/v1/auth/account-hint?username=<账号>`
  (`backend_gateway/app/api/auth.py`) —— 回 `account` / `needs_password` / `role` /
  `username` 四个字段。
  - 口径跟登录接口**完全一致** (`role == admin or password_required`) —— 有单测
    (`test_account_hint_agrees_with_login`) 盯着两边不许分叉, 分叉了用户就会莫名
    挨一次失败。
  - ⚠️ 它会暴露"账号存不存在"(跟登录接口的 `account_not_found` 同一类信息)。
    登录接口靠失败计数限流, 这个端点**不会失败** → 另有一套按 IP 的限流
    (`AUTH_HINT_LIMIT` 默认 120 次 / 5 分钟)。
- 前端 `views/Login/index.vue` 重写:
  - 免密账号 → **不摆密码框**, 按钮写「免密登录」, 绿色提示"直接回车即可";
  - 要密码的账号 → 摆出密码框 + 说清"该账号已设置密码";
  - 没开通 / 已停用 → **当场说清楚**, 不用试一次;
  - 管理员账号(纯账号名)→ 不再在输入框后面挂 `@twsc.com.cn` 后缀(那提示是错的);
  - 探测失败(后端不可达)→ 退回老路(提交时后端回 `password_required` 再展开),

### ⑦ 生产环境走**裸机模式**(决策 + 实测数据)

生产环境不方便容器化 → 定了**生产裸机、开发容器**。实测对比(本机真实数字):

| | 容器 | 裸机 | 差 |
|---|---|---|---|
| 磁盘·应用 | 镜像 2.0 GB | **117 MB**(venv 103M + 前端产物 1.9M) | 省 ~1.9 GB |
| 内存 | 556 MB | ~570 MB | **持平**(大头是 MySQL, 两边都要付) |
| 守护层 | Docker Desktop 进程 ~1.0 GB | 无 | 省 ~1 GB |
| 启动 | `docker compose up -d --build` | `tmctl.sh local install --auto` + `launchd install` | 持平 |
| 改一行代码 | 要 rebuild 镜像 | **从源码跑, 重启即生效(无漂移)** | 裸机省心 |
| 磁盘卫生 | 镜像/缓存会无限堆积(本机 57 GB) | 用多少占多少 | 裸机干净 |

**GitLab 才是真正的大头**: 镜像 5.99 GB + 内存 **4.2 GB**(是 TestMate 本体的 7 倍)。
⚠️ 但后端**根本没用 GitLab 的 REST API**(`app/core/git_sync.py`: 只走 SSH + git push/pull,
没有 PAT、没有 token 过期、没有 API 限流) → **远端只要是"能 SSH 的 git 仓库"就行**。

→ 生产决定: **用公司现成的 GitLab / 云 GitLab**, TestMate 只当客户端(0 磁盘 0 内存)。
换远端的四步已写进 `deploy/native/README.md` §6.9, 并且新增两条命令:

```bash
./deploy/native/tmctl.sh ssh show              # 看市场用的 SSH 公钥 → 贴到公司 GitLab
./deploy/native/tmctl.sh ssh trust <host[:port]> # 钉 host key(打印指纹, 人工核对)
```

⚠️ 为什么要 `ssh trust`: 后端用 `StrictHostKeyChecking=accept-new` —— 第一次连上就自动
信任那个 host key。开发机方便, **生产是隐患**(第一次连的是谁就永远信谁)。
`ssh trust` 改成**人工核对指纹后再钉**。

⚠️ 两个 known_hosts 别搞混: 裸机是 `deploy/native/runtime/ssh/known_hosts`
(`ssh trust` 写的就是它); Docker 模式是 `deploy/.env` 的 `GITLAB_KNOWN_HOSTS` 指向的那个。

### ⑩ 软件库落地(2026-10-28)

详细设计见 [`docs/specs/2026-10-28-software-library.md`](specs/2026-10-28-software-library.md)。要点:

| 改动 | 结果 |
|---|---|
| 新表 `software_items` / `software_versions` | 与「插件·技能·连接」彻底分家(那边真身在 GitLab, 这边真身在**服务端磁盘**) |
| 新 API `/api/v1/software` + 新页面 `/software` | 独立页面, 不塞进 `/market` 的 Tab; 前端视觉与市场页一致 |
| 上传走**原始字节流** | 不走 multipart —— starlette 会把文件先 spool 到系统临时目录, 5G 在临时目录**再存一份** |
| 下载走**短时票据** | 10 分钟有效的 JWT + `FileResponse` 流式回传; 不返回 blob(5G 的 blob 打爆浏览器内存), 不把长期 token 拼进 URL(会进 access_log) |
| 上架即上架 | 无审核队列, 发布权复用 `market_policy.can_publish`; 审计复用 `asset_audits`(`sw:<code>`) |
| 新增 4 个设置项 | `software.storage_path` / `max_size_mb`(默认 5G) / `keep_versions` / `public_download` |

⚠️ **踩过的三个坑**(都在 `deploy/native/selftest.sh` 里加了守门):

1. **nginx 的 `location /api/v1/software/` 结尾不能带斜杠**。nginx 对 `location /xxx/`
   会**自动 301 补斜杠**(像访问目录),而 FastAPI 的路由是 `/api/v1/software`(没斜杠)
   → 又 **307 弹回来** → 重定向死循环;而且 nginx 改写 Location 时按 `$host` 拼会**把端口吞掉**
   (`127.0.0.1:8081` → `localhost:80`)→ 最后 `ERR_CONNECTION_REFUSED`,软件列表整个加载不出来。
2. **launchd 的环境变量在 plist 里,不在 `backend.env`**。`local update` 以前只重新生成
   `backend.env` → `SOFTWARE_STORAGE_PATH` 到不了进程 → 后端默默用了兜底路径
   `<仓库>/data/software`,软件包落到了**仓库目录**里,没人发现。
3. **光重生成 plist 也不够** —— launchd 只在 bootstrap 那一刻读它,改完必须重新
   `bootout + bootstrap`(`kickstart` 重启的还是旧定义)。
   现在 `local update` 会重生成 plist **并且**重新装载(`launchd_reload_units`)。

⚠️ **两处 nginx 都要改**(裸机 `deploy/native/units/nginx.conf.tpl` + 容器 `frontend_web/nginx.conf`):
`client_max_body_size 6g` + `proxy_request_buffering off` + 超时 3600s。漏一处就 413。

⚠️ **软件目录不进 `tmctl.sh backup`**(体积太大)—— 要备份得单独拷这个目录。

实测(裸机):200MB 包 sha256 一致 · nginx 缓冲目录全程 0KB · 后端内存 +3MB(内存恒定) ·
200MB 下载 0.35s。验收: `scripts/e2e_software.js` 26/26。

### ⑫ 软件库卡点了跳进工具运行页(2026-10-28)

1. **e2e 只断言了"卡片不是规划中"** —— 那是后端 status,跟跳转无关.

### ⑬ 软件库上传抽屉的四个坑(2026-10-28)

用户让看上传界面, 截图时发现一串真问题, 逐个挖出来的:

1. **「适用平台」下拉显示英文 `Select`** —— Element Plus 的默认 placeholder.
   整个界面都是中文, 夹一个英文很扎眼 → 加 `placeholder="不限"`.
2. **发新版本时, 上一版的「发布与更新说明」直接躺在新版本的输入框里** ——
   抽屉是**常驻组件**(不是 v-if 重建), 草稿没人清.
   现在关闭抽屉时 `resetDraft()` 清干净(说明 / 功能清单 / 标签 / 表单 / 文件).
3. ⚠️ **只清 Vue 状态不够 —— 浏览器里的 `input.files` 还得清**.
   Vue 状态清了但 `input.files` 还留着上次的文件时, 浏览器判断"文件列表没变"
   → **不再派发 change** → `onPick` 不跑 → 用户选了新文件, 界面纹丝不动,
   实际提交的还是**旧文件**. 这是最隐蔽的一个.
   现在 `clearDomFile()` 额外做 `input.value = ''`.
4. ⚠️ **两个抽屉叠在一起** —— el-drawer 的 z-index 是"打开时递增"分配的,
   同一个抽屉实例 (create → version) 复用第一次的 z-index, 比详情抽屉小 →
   **发新版本的表单被详情抽屉压住**, 用户点了"发新版本"只看见详情.
   现在 `openVersion()` 先关详情抽屉再开; 发完新版本自动回到详情, 直接看到新版本历史.

另有两个"改 A 坏 B"的坑, 记下来:

- **在"打开时"清 file 会让文件选不上了** —— 打开瞬间改状态会让 Vue 立刻 patch 掉
  刚挂上的 DOM, 紧接着的 change 事件就丢了. 挪到**关闭时**做就没问题.
- **`form.value = emptyForm()` 换掉整个对象, el-input 绑定的旧值不会同步到 DOM** ——
  输入框里还留着上一次的简介. 必须 `Object.assign(form.value, emptyForm())` 逐字段重置.

⚠️ **e2e 断言也踩了坑**: 以前发新版本传的是**同一个文件**, 正好绕开了"文件列表没变"
这个场景, bug 藏了很久. 现在改成传**内容不同**的文件 + 断言新版本的 sha256,
并加一条「更新说明是空的」断言 —— 旧代码下这条精准 FAIL (28/29), 新代码 29/29.

### ⑮ 选填信息栏 + 多版本并存(2026-10-28)

用户提了两件事: ① 上架和详情要能展示「安装说明」「注意事项」这类**可选**信息栏;
② **一个软件要挂两个不同的版本, 两个都有用** —— 该怎么管。

#### ① 选填信息栏

| 字段 | 存哪 | 详情里怎么显示 |
|---|---|---|
| 安装说明 `install_steps` | `software_items` | **有序列表**(一行一条) |
| 注意事项 `caveats` | `software_items` | **醒目提示块**(黄底 + ⚠) |

- `PUT /software/{code}` 能补写 (上架时忘了写, 后面再补).

#### ② 多版本并存

原来后端**已经是**条目 1:N 版本(旧版仍可下), 但"两个版本都有用"这个场景缺三样东西:

| 能力 | 做法 | 后端 |
|---|---|---|
| **变体标签** | 给版本起个小名, 如「Windows版」「LTS版」「通用版」 | `software_versions.variant` (选填) |
| **推荐下载版本** | 手动指定该下哪个, 头部「⬇ 下载」跟着走 | `software_versions.is_default` |
| **单版本下架** | 只撤掉传错的那一版, 其他版本照旧能下 | `DELETE /software/{code}/versions/{version}` |

关键设计:

- **`is_default` 放在版本行上, 不放条目上** ——
  "该下哪个"天然是版本的属性; 换推荐只是把某一行的标记挪走.
  条目上的 `version` 字段是"当前版本指针"(发新版本自动切), 它回答"最新的是哪个",
  跟 is_default 回答的"该下哪个"是**两回事**.
- **推荐位必须唯一** —— 发新版本(默认接管推荐)时, 后端自动把旧版的推荐标记摘掉;
  手动设推荐时同理. 不唯一的话前端不知道该指哪.
- **发新版本时可以选「不接管推荐位」** —— 适合"LTS 版还在给老环境用"的情况.
  抽屉里那个复选框默认**勾上**(发新版=让大家下新的), 主动取消才不抢.
- **推荐版本永远不被自动清理** —— `keep_versions` 清理老版本时, 推荐的那一版豁免.
  否则悄悄把用户特意留着的版本清掉, "该下哪个"就悬空了.
- **单版本下架**: 删掉最后一个能下载的版本 → 条目一起下架(不能空着上架);
  删别的版本 → 条目照旧上架, 其余版本照旧能下.
- 详情页版本行: 变体标签(蓝色)、推荐(绿色)、⬇下载 / ⭐设为推荐 / 下架这版.
  只有一个版本时**不显示**"共 N 个版本"那句 —— 多余.

#### 这轮踩到的坑

- ⚠️ **SQLAlchemy 的 `synchronize_session` 跟 SQL 实际匹配范围不一致** ——
  发新版本时"把旧版推荐标记摘掉"那条 UPDATE, WHERE 里要排除新版本自己.
  但新版本刚 `session.add()` 还没 flush 时 `ver.id` 是 None → 拼出来的 `id != NULL`
  在 SQL 里**恒不成立**, 而 ORM 的 'evaluate' 策略又在 Python 侧按同样条件改了内存对象 ——
  两边不一致, 推荐标记直接错乱.
  **修法**: 先 `await session.flush()` 拿到 `ver.id`, 再执行 UPDATE,
  并加 `.execution_options(synchronize_session=False)` (手工改比 ORM 猜得准).
- ⚠️ **MySQL 的 TEXT 列不能带 DEFAULT** ——
  `ALTER TABLE ... ADD COLUMN install_steps TEXT NOT NULL DEFAULT ''` 报
  `BLOB, TEXT, GEOMETRY or JSON column can't have a default value`.
  **修法**: 先加成可空列 → `UPDATE` 回填空串 → 再 `MODIFY ... NOT NULL`.
- ⚠️ **alembic revision id ≤ 32 字符** —— 0026 最初叫 `0026_sw_install_notes_and_variants`
  (35 字符), DDL 全执行完了但版本号写不进 `alembic_version.version_num`.
  改名 + `alembic stamp` 补上 (DDL 是非事务的, 列已经建好了, 别重复跑).
- ⚠️ **组件测试里抽屉靠 `watch(modelValue)` 触发读取** ——
  一上来就传 `modelValue: true` 的话 watch 不会 fire (没变化), 详情永远是空的.
  必须先挂成 `false`, 再 `setProps({ modelValue: true })`.
- ⚠️ **vi.mock 的工厂函数会被提升** —— mock 里引用模块级的 `const getSoftware`
  会 TDZ 报错, 必须用 `vi.hoisted`.
- **e2e 里 el-checkbox 不能只点 `input`** —— Element Plus 把真正的 input 藏起来了,
  要点 `.el-checkbox__label`.

```

只改 DB 的话: 同步器下一次就从远端把老分类拉回来 —— **GitLab 是真源, DB 只是镜像**。
脚本 `python3 scripts/migrate_categories.py --apply` 一次做完并 commit+push, 退出前回读
DB / index.json / manifest 三处核对。

#### ⚠️ 两个坑(下次改脚本必看)

1. **`git mv` 之后再 `git add -A -- <旧路径>` 会直接失败**:
   `fatal: pathspec 'assets/skills/diagnose/x' did not match any files`
   (旧路径已经被 `git mv` 从索引里删了, 既不在索引也不在工作区).
   但 `git commit -- <旧路径> <新路径>` 是**好的** —— 提交的临时索引是
   "HEAD + pathspec 对应的工作区内容", 旧路径的删除记录在索引里会一起进提交.
   → 所以 `git_sync.sync_paths_blocking` 加了 `commit_paths` 参数:
   **`paths` 给还能 add 的(新路径+index.json), `commit_paths` 给要进提交的(新+旧+index.json)**.
   漏了旧路径, 远端会**同时留着新旧两份目录**.

2. **迁移方案要按**工作区 manifest** 算, 不能按 DB 算**:
   真源是 GitLab(工作区是它的本地检出), DB 只是镜像.
   按 DB 算的话, "DB 已迁 / 工作区未迁"(或反过来)时会算出**空计划** ——
   脚本啥也不干, 看着像"没活儿", 其实根本没迁完.

#### 分类别名必须**链式**解析

#### 顺手修掉的两个真 bug(截图验收时撞出来的)

#### ② 新增「🔌 体检存储目录」—— 换根目录**不会自动搬文件**

这是本轮最实的一个功能。改 `software.storage_path` 只是**改指针**,
老文件还躺在旧目录里 —— 不体检的话, 管理员改完路径照样上传成功、下次下载 404,
而且完全不知道为什么。

新增端点 `POST /api/v1/settings/test/software_storage`(admin only):

```
ok        → 可写 · 软件库已占 0.0 GB / 磁盘剩余 200.9 GB · 文件都在  路径 …
warn      → 目录不存在: <root> —— 建出来或者换个已经存在的路径
warn      → 目录存在但不可写: <root> —— 权限不对 (容器里通常是没挂卷)
```

`detail` 里给 `root` / `exists` / `writable` / `used_bytes`(软件库自身) /
`free_bytes`(整盘剩余) / `missing_count` / `missing[]` /

`source` 特别重要: 裸机模式下路径来自环境变量 `SOFTWARE_STORAGE_PATH`,
DB 里改不动它; 不说清来源, 管理员在设置页改了却"没生效"会以为功能坏了。

> ⚠️ **为什么不复用 `/software/path-check`**: 那个接口返回的是**软件库领域**结构
> (missing 列表带 code/version), 设置页要的是**能不能用**的一句话结论。
> 两个用途、两套受众, 别混。

#### ⚠️ 踩过的坑: `used_bytes` 有**两个**,含义不同

```

拿错的话设置页会显示「**软件库占了 725GB**」—— 那是一整块盘。

1. **嵌套 `ul` 在 flex 的 `li` 里会被压扁**:

### ⑲ 审核总开关: 一个开关管上架 + 下架 (2026-10-28 晚)

用户要求: 「上架更新和下架审核可以在设置中加个开关, 默认开启, 关闭后上传者可以免审核」。

#### 拍板的两个决定

1. **一个开关管两件事** —— 复用已有的 `marketplace.review.enabled`, **不新增第二个设置项**。
   它在设置页「🗂️ 能力墙 → 📦 资产 → 🧩 插件·技能·连接」分组下, 本来就是个 bool 开关。
2. **免审下架 = 自助下架并保留文件**(进 `unpublished` 态),
   **不给作者「直接删除」的权限** —— 删除不可逆, 而市场是共享的(别人可能正在用)。
   要彻底删除仍然只能管理员来(申请制那条路, 或 admin-only 的 `DELETE /{code}`)。

#### 开关关掉之后的行为

| | 开关开 (默认) | 开关关 (免审) |
|---|---|---|
| 上传 / 更新 | 进「待审核」, 管理员通过才在市场可见 | **直接上架**, 不用等 |
| 下架 | **申请制**: 作者申请 → 管理员确认 → 资产被**彻底删除** | **自助下架**: 立刻从货架消失, **文件保留**, 随时可「重新上架」 |
| 彻底删除 | 只能管理员 | 只能管理员(**不变**) |

#### 实现要点

- **状态机新增动作 `take_down`**(`app/core/market_state.py`):
  `((PUBLISHED,), UNPUBLISHED, "author")`, 审计标签「自助下架 (免审核, 文件保留)」。
  这条路径以前**根本不存在** —— 状态机定义了 `unpublished` 态、前端也有徽标和「重新上架」按钮,
  但没有端点能进这个态(见 §9 第 7 条)。
- **`POST /{code}/unpublish` 加免审分支**: 读 `_setting_bool("marketplace.review.enabled", True)`,
  为假 → `_set_publish_state(publish_status="unpublished", action="take_down")` + 发 `unpublish` 通知;
  为真 → 原来的申请制(`unpublish_pending`)。`confirm_code` 校验在两个分支**之前**, 绕不过去。
- **`GET /assets/config` 暴露 `review_enabled`**(**生效值**, 不是 schema 默认值) → 前端据此改按钮文案与确认框。
- **通知**: 事件 key 仍是 `unpublish`(开关映射靠 key, 不能乱换), 只用 `title_override`
  换标题「📦 资产已下架 (文件保留)」—— 免审下架**不是**彻底删除, 标题别再写 🗑。

#### ⚠️ 踩过的坑

1. **Vue Boolean prop 的「缺省强转成 false」**:
   `reviewEnabled?: boolean` 不显式给 `default: undefined` 的话, 父组件没传时
   `props.reviewEnabled` 是 `false` 而不是 `undefined` ——
   「取不到开关 → 保守按开着处理」会反过来变成「取不到 → 按免审处理」, **方向正好反了**
   (拿不准时该多走一次审核, 而不是少走)。
   修法: `withDefaults(defineProps<...>(), { reviewEnabled: undefined })`。
2. **改开关语义会连带打穿一批单测**: 以前有 17 处单测拿
   `marketplace.review.enabled="false"` 当「让上架免审」的捷径。
   现在这个开关关掉后**下架也变自助**, 申请制那条路根本测不到 →
   全部改成「开着 + 代管理员 approve 一下」来拿在架资产。
   同时把 `_publish_asset`(只上传) 和 `_published_asset`(上传 + 代通过) 拆开 ——
   要 pending 资产的用例不能代通过。
3. **单测里断言「文件是否保留」要查工作区目录**, 不能查远端裸库 ——
   单测没有后台 worker, 远端根本没被推, 「文件还在」和「文件被删了」是**同一个假象**。
4. **e2e 必须用非管理员账号测**: `marketplace.review.admin_self_approve`(默认开)
   让管理员自己的上传免审核 —— 拿 admin 测, 开关开开关都是 `published`, 根本测不出效果。
   (e2e 里要建发布者账号 + 加 `marketplace.publisher_usernames` 白名单, 结束必须还原+删号。)
5. **e2e 上传走 `package` 字段, 不是 `files`**: `files` 是**多文件文本**上传,
   塞 zip 进去后端报「不是 UTF-8 文本」; 而且包名必须与资产 code 一致(后端 `_assert_naming` 会拦)。
6. **市场页默认停在「插件」tab**: 技能资产根本不渲染 ——
   e2e 找不到卡片不是数据的问题, 是 tab 没切过去。
7. **返回字段别叫 `reviewed`**: 两条路返回时都「还没被审核过」, 这个字段等于没信息。
   改成 `needs_review`(申请制 `true` / 自助 `false`)。
8. **ElMessageBox 是纯文本, 不渲染 Markdown**: 确认框里写 `**立刻生效**` 会把星号**原样显示出来**
   (设置页的 description 才是走 Markdown 的)。弹窗里一律用「」。
9. **`_ACTION_COMMIT_TEXT` 别漏**: 新动作不在这个表里, git commit 文案会落成兜底的「更新资产」——
   提交历史里就看不出这次到底是上架还是下架。`take_down` → 「自助下架」。

### ⑳ 软件标识自动生成 + 文件名校验 + 「下架删目录」全流程修复 (2026-10-28 晚)

用户提了两个问题:

1. **「code 不要用户来填写, 自动根据软件英文名称来维护」** + 「上架的软件包名称必须是英文数字和标准字符, 上架时校验」。
2. **「我全下架了多个版本, 但重新设置过的根目录下的这个目录没删除」** (`software/dify-web-entrypoint2`) —— 「看看这个流程的坑还有哪些」。

#### 问题 ①: 软件标识(code)改成自动派生 + 文件名当场校验

**拍的板**: 「软件英文名称」= **上传的软件包文件名**(去掉扩展名)。理由: 中文「软件名」生成不出 code;
用户自己那次的 code (`dify-web-entrypoint2`) 本来就取自 `dify-web-entrypoint.sh`;
而且「软件包的名称必须是英文数字」这句话指向的也是文件名。→ **不新增输入框**, code 选完文件后**只读自动生成**。

| | 改前 | 改后 |
|---|---|---|
| code 谁定 | 用户手填 | **后端按文件名派生** (`code_from_file_name`) |
| code 撞名 | 409 冲突 | **自动加序号** (`base2` / `base3`, 最多 999 次) |
| 文件名不合规 | `sanitize_filename` **静默改名** | **当场 422 拒绝** (中文/空格/括号/以点开头) |
| 前端 | 可编辑输入框 | **只读** + 「自动」标签, 选文件时实时显示 |

- 派生规则(前后端**一字不差**): 去扩展名 → 转小写 → 非法字符换 `-` → 合并连续 `-` → 去掉首尾 `-._` → 截 64 位 → 不足 2 位补齐。
- 文件名规则 `FILE_NAME_RE = ^[A-Za-z0-9][A-Za-z0-9._-]{0,199}$`(以字母/数字开头)。
- **为什么不再 sanitize**: 静默改名用户不知道, 下载回来名字对不上更麻烦。`sanitize_filename` 降级成**兜底**。
- 空 `file_name` 仍然**允许**(兜底 `{code}-{version}.bin`) —— 不破坏既有 API 契约(老调用方只传元数据)。
- 前端新增 `validateFileName` / `codeFromFileName`(`frontend_web/src/views/Software/softwareForm.ts`), 有 12 条新单测锁住。

#### 问题 ②: 「下架删目录」的三个坑 + 修法

**根因 A(用户报的)**: 逐个「下架版本」只删 `<root>/<code>/<version>/`,
上层 `<root>/<code>/` 的**空壳目录没人清理** → 用户看到目录还在。

**根因 B(更大的坑)**: 落库的 `file_path` 是**相对路径**(`code/version/file_name`),
而所有删除/下载逻辑都用**当前** root 拼它 → 管理员改了 `software.storage_path` 之后,
「当前根 + 相对路径」找不到老文件了 —— **文件还在旧根躺着, 但下载 404、删除删不掉**, 成了删不掉的孤儿。
实测现场: 设置项根 = `TestMate/software`, 环境变量根 = `deploy/native/runtime/data/software`(文件实际在这), 默认根 = `data/software` —— **三个根并存**。

**根因 C**: 软删条目(`delete_software`)按设计**保留文件**, 只有 `purge` 才真删; 而 `purge` 也只删当前 root 下的。

**修法(不引入 alembic 迁移)**:

- **多根候选** `software_store.candidate_roots(当前根, 历史根)`:
  顺序 = 设置项根 → `software.storage_path_history` → 环境变量根 → 默认根(去重)。
  ③④ 天然覆盖「改设置项之前」的存放位置, 所以绝大多数情况不用额外维护。
- **查找**: `locate_under` / `locate_version_dir` / `locate_item_dir` —— 依次在候选根里找。
  下载端点改用 `locate_under` → **换根后老文件照样能下**。
- **删除**: `remove_version_dir_anywhere` / `remove_item_dir_anywhere` —— **所有**候选根里的同名目录都删
  (改过好几次根目录时同一路径可能在两个根都存在, 只删找到的第一个不够)。
- **空壳清理**: 删完版本顺手 `remove_item_dir_if_empty(root, code)` → 这就是用户报的那个目录。
- **换根时记历史**: `PUT /settings/software.storage_path` 触发 `_remember_old_storage_root` →
  旧根归一成绝对路径追加进新设置项 `software.storage_path_history`(最多 20 个)。
- **体检端点把「缺」拆成两类**(设置页「体检存储目录」+ `GET /software/path-check`):
  · **missing** —— 当前根没有, 但**别的根**里找到了(文件没丢, 下载/删除会自动去找)
  · **lost** —— 所有候选根都没有(真丢了)
  · 另外报告**孤儿目录**(根下有目录但 DB 里没这个 code)。
- 软删(`delete_software`)**仍然保留文件**(设计如此), 彻底删除走 `purge` —— `purge` 现在会清所有候选根。

#### ⚠️ 踩过的坑

1. **钩子在提交之后才读旧值 → 历史根永远记不上**:
   `update_setting` 里先 `commit()` 再调 `_remember_old_storage_root`, 函数内部回读数据库拿到的**已经是新值** →
   `old == new` 直接 return。修法: **写入新值之前**把旧值抓出来传进去(已加单测 `test_changing_storage_root_remembers_old_root`)。
2. **`select(...)` 忘了 `.scalars()`**: `await session.execute(select(SoftwareItem.code)).all()` 拿到的是 **coroutine**,
   报 `AttributeError: 'coroutine' object has no attribute 'all'` —— 两处(software.py / settings.py)都踩了。
3. **图标全局唯一(另一条并行会话加的规则)**: 新写的「撞名加序号」用例没给唯一图标 →
   先撞图标 409。**造新用例时记得图标也要换**。
4. **前端 code 只读后提示要改口径**: 用户改不了 code, 所以校验失败时的提示要说「**换个软件包文件名**」,
   而不是「只能用小写字母…」(他改不了, 只会懵)。
5. **别用行号切 Vue 模板**: 行号会整体错位 —— 用 `src.index('...')` 内容定位。

#### 实测验证(只跑「下架删目录」这条流程, 真实实例走平台 API)

```
切到旧根上架 tm-verify-b (code 自动生成) → 文件落在旧根
切回新根 → storage_path_history 自动记下旧根 ✅
换根后下载 → HTTP 200 / 11 字节 / 内容一致 ✅        ← 根因 B
下架版本 → 旧根里 tm-verify-b/1.0.0 与空壳 tm-verify-b/ 全删 ✅ ← 根因 A+B
当前根对照组 → 空壳目录也删 ✅
purge 4 个条目 → 遗留的 dify-web-entrypoint / dify-web-entrypoint2 目录消失 ✅
收尾体检 → missing=1(xx 在旧根, 没丢) lost=0 orphan=0
```

顺手清掉了用户遗留的两个空壳条目(`dify-web-entrypoint` / `dify-web-entrypoint2`, 都是今天测试留下的软删条目);
`xx` 条目(`xx/1.0.0/mineru.json`)按约定**没动**。

### ㉑ 「下架这版」成功却报「软件 xxx 不存在」(2026-10-28 晚)

用户截图: 点「下架这版」→ 绿色提示「版本 1.0.0 已下架」✓, 紧接着两条红色「软件 dify-web-entrypoint 不存在」。

#### 根因

后端 `delete_version` 里有一条**设计**: 删掉**最后一个**能下载的版本时, 条目不能空着上架,
所以会连带把条目软删(`publish_status="hidden"` + `deleted_at=utcnow()`)。
→ 这之后 `GET /software/{code}` 必然 404。

前端不知道这件事, 下架成功后照旧 `await load()` 刷新详情 → 404 → 弹红错;
`emit('changed')` 又让父组件刷新 `refreshKey`, watch 再 `load()` 一次 → **弹两条**。
也就是说: **操作是成功的, 但界面在报失败**。

#### 修法(前端为主, 后端补一个信号)

- **后端**: `DELETE /{code}/versions/{version}` 的返回体加 `item_unpublished`(条目是否被连带下架)
  和 `remaining_versions` —— 审计里本来就有这个字段, 现在正式返回给前端。
- **前端**:
  · `item_unpublished` 为真 → 成功提示改成「版本 x 已下架 · 这是最后一个版本, 软件已一并下架」,
    **关抽屉 + 刷新列表, 不再查详情**(查了必然 404);
  · `load()` 遇到 **404 → 静默关抽屉**, 不弹红错(兜住所有路径, 比如父组件 refreshKey 触发的二次加载);
  · 「下架这版」的确认框在**只有一个可下载版本**时改口径:
    「这是**最后一个**可下载版本 —— 下架后这个软件会**一起从软件库里消失**」;
  · 「下架软件」(`purge`) 的顺序改成**先关抽屉再刷新列表** —— 反过来的话父组件刷新会在抽屉还开着时查一次详情 → 404。

#### 实测(真实 Chrome)

造一个只有一个版本的软件 → 打开详情 → 点「下架这版」→ 确认:

```
提示: ["版本 1.0.0 已下架 · 这是最后一个版本, 软件已一并下架"]   ← 只有绿色, 没有红色
抽屉已关闭 ✅   列表里条目已消失 ✅   页面 JS 错误: 无 ✅
```

单测: 后端 2 条(返回体字段)、前端 3 条(关抽屉 / 不报错 / 404 静默)。

## 7. 容易踩的坑(这个项目特有的)

1. **两种部署模式不能同时跑** —— 资产市场的 job 队列是进程内 `asyncio.Queue`,
   不跨进程。两个后端各有一份队列 → 同一个 job 被两个进程抢 → git `index.lock`
   冲突 / 重复推 GitLab。切模式要停 **frontend + backend 两个**;
   只停 backend 的话, 那个端口会变成「页面能开、接口全 502」的假象。
2. **Docker 模式与裸机模式的库是各的** —— 换模式不会自动带数据过去,
   要搬: `mysqldump` → `tmctl.sh local db import <dump.sql>`。
3. **改 `deploy/native/.env` 的端口后要重跑 install** —— 运行时的配置由
   `backend.env` / `nginx.conf` 派生, 只改 `.env` 不生效。
4. **改前端代码必须重建** —— 裸机模式的 bundle 是 `deploy/native/runtime/frontend`
   (`npm run build` + 拷过去), Docker 模式则要 `--build` 重建镜像。
5. **用户可见文案里不许出现「智能体」「知识库存」「Dify」** —— 主词统一是「能力」。
6. **死路菜单项比没有更糟** —— 点了没用的项比不提供更伤。
7. **前端错误提示不许把 axios 原始报文甩给用户** —— 一律走 `utils/httpError.ts`。
8. **`tmctl.sh` 的选项解析**: `local` / `launchd` 后面第一个词才是命令, 全局选项
   写在命令后面也能认(这条修在 `feature/native-zero-container` 上, 已合并)。
9. **launchd 的服务停不掉, 只能卸载** —— `RunAtLoad + KeepAlive` 的单元,
   `launchctl bootout` 之外没法"暂停": 一停它就被拉回来。
   要切回 Docker 模式 → `tmctl.sh launchd uninstall`(开机自启也一并没了)。
10. **容器模式停掉后, 后端单测的 Redis 探针会失败** —— 测试环境的 `REDIS_HOST`
    默认是容器名 `redis`, 本机解析不了 → `/health/ready` 返 503。
    跑 readiness 相关的测试时要把 Redis 探针一并 mock 掉
    (见 `tests/test_market_health_signal.py` 的 `_patch_deps`)。
