### ② 后端自动双向改写「本机地址」—— 不用再改 `/etc/hosts`

`host.docker.internal` 是**容器里**访问宿主用的名字; 裸机后端跑在宿主上, 那个名字
从宿主侧连不通(解析到 Docker 虚拟网卡 198.18.x.x, TCP 能连上但没有服务应答)。

以前只有一条路: `sudo tmctl.sh local hosts fix`(改宿主 `/etc/hosts`, 要 root)。
现在后端按"自己跑在哪"自动改写:

| 后端在哪 | 填 `127.0.0.1` / `localhost` | 填 `host.docker.internal` |
|---|---|---|
| 容器里 | → `host.docker.internal` | 原样 |
| 宿主上 | 原样 | → `127.0.0.1` |

- HTTP: `backend_gateway/app/core/settings_store.py` 的 `_rewrite_loopback`
- git 远端(SSH): `backend_gateway/app/core/git_sync.py` 的 `_rewrite_remote`(新增)

**同一个设置值在两种部署模式下都通** —— 切模式不用改设置, 也不用改 hosts。
`local hosts check/fix` 保留着, 只给"别的工具(curl/ssh)也要用这个别名"用。

### ③ 修掉一个让"全新部署起不来"的真 bug

`init_db()` 的 stamp 兜底把"版本表不存在"一律当成"老环境用 create_all 建的",
于是**全新空库**被 stamp 到 head —— 版本号是 head 但**一张表都没建**,
后端报 `Table 'testmate.agents' doesn't exist`, 而 alembic 说"已是最新"。

而且迁移链本身**不能从零跑**: `0001_initial` 建的是远古 agents 表, `0003` 去
`ALTER` 一个**从没被迁移建过**的列 (`category`) —— 0001~0022 是"补丁叠在 create_all
之上"的, 前提是库已经建好了。

现在按"库里有没有业务表"分流: 没有 → 用模型建出当前完整 schema (`create_all`) +
`stamp head`; 有 → 照旧按版本号 `upgrade`。

### ⑥ 登录页改成"免密优先"—— 要密码的账号才摆密码框

后端才回 `password_required` → 前端这才展开密码框。**白挨一次失败**, 而且那一次

    (`test_account_hint_agrees_with_login`) 盯着两边不许分叉, 分叉了用户就会莫名
    挨一次失败。
  - ⚠️ 它会暴露"账号存不存在"(跟登录接口的 `account_not_found` 同一类信息)。

### ⑦ 生产环境走**裸机模式**(决策 + 实测数据)

生产环境不方便容器化 → 定了**生产裸机、开发容器**。实测对比(本机真实数字):

| | 容器 | 裸机 | 差 |
|---|---|---|---|
| 磁盘·应用 | 镜像 2.0 GB | **117 MB**(venv 103M + 前端产物 1.9M) | 省 ~1.9 GB |
| 内存 | 556 MB | ~570 MB | **持平**(大头是 MySQL, 两边都要付) |
| 守护层 | Docker Desktop 进程 ~1.0 GB | 无 | 省 ~1 GB |
| 启动 | `docker compose up -d --build` | `tmctl.sh local install --auto` + `launchd install` | 持平 |
| 改一行代码 | 要 rebuild 镜像 | **从源码跑, 重启即生效(无漂移)** | 裸机省心 |
| 磁盘卫生 | 镜像/缓存会无限堆积(本机 57 GB) | 用多少占多少 | 裸机干净 |

**GitLab 才是真正的大头**: 镜像 5.99 GB + 内存 **4.2 GB**(是 TestMate 本体的 7 倍)。
⚠️ 但后端**根本没用 GitLab 的 REST API**(`app/core/git_sync.py`: 只走 SSH + git push/pull,
没有 PAT、没有 token 过期、没有 API 限流) → **远端只要是"能 SSH 的 git 仓库"就行**。

→ 生产决定: **用公司现成的 GitLab / 云 GitLab**, TestMate 只当客户端(0 磁盘 0 内存)。
换远端的四步已写进 `deploy/native/README.md` §6.9, 并且新增两条命令:

```bash
./deploy/native/tmctl.sh ssh show              # 看市场用的 SSH 公钥 → 贴到公司 GitLab
./deploy/native/tmctl.sh ssh trust <host[:port]> # 钉 host key(打印指纹, 人工核对)
```

⚠️ 为什么要 `ssh trust`: 后端用 `StrictHostKeyChecking=accept-new` —— 第一次连上就自动
信任那个 host key。开发机方便, **生产是隐患**(第一次连的是谁就永远信谁)。
`ssh trust` 改成**人工核对指纹后再钉**。

⚠️ 两个 known_hosts 别搞混: 裸机是 `deploy/native/runtime/ssh/known_hosts`
(`ssh trust` 写的就是它); Docker 模式是 `deploy/.env` 的 `GITLAB_KNOWN_HOSTS` 指向的那个。

### ⑩ 软件库落地(2026-10-28)

详细设计见 [`docs/specs/2026-10-28-software-library.md`](specs/2026-10-28-software-library.md)。要点:

| 改动 | 结果 |
|---|---|
| 新表 `software_items` / `software_versions` | 与「插件·技能·连接」彻底分家(那边真身在 GitLab, 这边真身在**服务端磁盘**) |
| 新 API `/api/v1/software` + 新页面 `/software` | 独立页面, 不塞进 `/market` 的 Tab; 前端视觉与市场页一致 |
| 上传走**原始字节流** | 不走 multipart —— starlette 会把文件先 spool 到系统临时目录, 5G 在临时目录**再存一份** |
| 下载走**短时票据** | 10 分钟有效的 JWT + `FileResponse` 流式回传; 不返回 blob(5G 的 blob 打爆浏览器内存), 不把长期 token 拼进 URL(会进 access_log) |
| 上架即上架 | 无审核队列, 发布权复用 `market_policy.can_publish`; 审计复用 `asset_audits`(`sw:<code>`) |
| 新增 4 个设置项 | `software.storage_path` / `max_size_mb`(默认 5G) / `keep_versions` / `public_download` |

⚠️ **踩过的三个坑**(都在 `deploy/native/selftest.sh` 里加了守门):

1. **nginx 的 `location /api/v1/software/` 结尾不能带斜杠**。nginx 对 `location /xxx/`
   会**自动 301 补斜杠**(像访问目录),而 FastAPI 的路由是 `/api/v1/software`(没斜杠)
   → 又 **307 弹回来** → 重定向死循环;而且 nginx 改写 Location 时按 `$host` 拼会**把端口吞掉**
   (`127.0.0.1:8081` → `localhost:80`)→ 最后 `ERR_CONNECTION_REFUSED`,软件列表整个加载不出来。
2. **launchd 的环境变量在 plist 里,不在 `backend.env`**。`local update` 以前只重新生成
   `backend.env` → `SOFTWARE_STORAGE_PATH` 到不了进程 → 后端默默用了兜底路径
   `<仓库>/data/software`,软件包落到了**仓库目录**里,没人发现。
3. **光重生成 plist 也不够** —— launchd 只在 bootstrap 那一刻读它,改完必须重新
   `bootout + bootstrap`(`kickstart` 重启的还是旧定义)。
   现在 `local update` 会重生成 plist **并且**重新装载(`launchd_reload_units`)。

⚠️ **两处 nginx 都要改**(裸机 `deploy/native/units/nginx.conf.tpl` + 容器 `frontend_web/nginx.conf`):
`client_max_body_size 6g` + `proxy_request_buffering off` + 超时 3600s。漏一处就 413。

⚠️ **软件目录不进 `tmctl.sh backup`**(体积太大)—— 要备份得单独拷这个目录。

实测(裸机):200MB 包 sha256 一致 · nginx 缓冲目录全程 0KB · 后端内存 +3MB(内存恒定) ·
200MB 下载 0.35s。验收: `scripts/e2e_software.js` 26/26。

### ⑫ 软件库卡点了跳进工具运行页(2026-10-28)

用户反馈"点软件库卡进去是参数配置/运行/重置那个页" —— 根因在**后端 seed 同步**:

`seed_agents()` 的 `sync_keys` 里**没有 `route`** → seed 同步时**从不更新已有行的 route**。
库里 `software-library.route` 一直是 NULL → 前端 `capabilityRouteName()` 拿到 NULL 就回落到
`'tool-runner'` → 点卡跳进 `/c/software-library`(工具运行页) —— 用户看到的死路。

⚠️ 为什么之前没测出来(两个漏测点,都补了):

1. **e2e 只断言了"卡片不是规划中"** —— 那是后端 status,跟跳转无关.
   现在补了「点卡 → pathname **精确**等于 `/software`」+「不是 `/c/` 工具运行页」+
   「页面上有上传入口、不是参数配置页」三条断言.
2. **断言自己写错了还假通过** —— 原来用 `url.includes('/software')`,

### ⑬ 软件库上传抽屉的四个坑(2026-10-28)

用户让看上传界面, 截图时发现一串真问题, 逐个挖出来的:

1. **「适用平台」下拉显示英文 `Select`** —— Element Plus 的默认 placeholder.
   整个界面都是中文, 夹一个英文很扎眼 → 加 `placeholder="不限"`.
2. **发新版本时, 上一版的「发布与更新说明」直接躺在新版本的输入框里** ——
   抽屉是**常驻组件**(不是 v-if 重建), 草稿没人清.
   现在关闭抽屉时 `resetDraft()` 清干净(说明 / 功能清单 / 标签 / 表单 / 文件).
3. ⚠️ **只清 Vue 状态不够 —— 浏览器里的 `input.files` 还得清**.
   Vue 状态清了但 `input.files` 还留着上次的文件时, 浏览器判断"文件列表没变"
   → **不再派发 change** → `onPick` 不跑 → 用户选了新文件, 界面纹丝不动,
   实际提交的还是**旧文件**. 这是最隐蔽的一个.
   现在 `clearDomFile()` 额外做 `input.value = ''`.
4. ⚠️ **两个抽屉叠在一起** —— el-drawer 的 z-index 是"打开时递增"分配的,
   同一个抽屉实例 (create → version) 复用第一次的 z-index, 比详情抽屉小 →
   **发新版本的表单被详情抽屉压住**, 用户点了"发新版本"只看见详情.
   现在 `openVersion()` 先关详情抽屉再开; 发完新版本自动回到详情, 直接看到新版本历史.

另有两个"改 A 坏 B"的坑, 记下来:

- **在"打开时"清 file 会让文件选不上了** —— 打开瞬间改状态会让 Vue 立刻 patch 掉
  刚挂上的 DOM, 紧接着的 change 事件就丢了. 挪到**关闭时**做就没问题.
- **`form.value = emptyForm()` 换掉整个对象, el-input 绑定的旧值不会同步到 DOM** ——
  输入框里还留着上一次的简介. 必须 `Object.assign(form.value, emptyForm())` 逐字段重置.

⚠️ **e2e 断言也踩了坑**: 以前发新版本传的是**同一个文件**, 正好绕开了"文件列表没变"
这个场景, bug 藏了很久. 现在改成传**内容不同**的文件 + 断言新版本的 sha256,
并加一条「更新说明是空的」断言 —— 旧代码下这条精准 FAIL (28/29), 新代码 29/29.

### ⑮ 选填信息栏 + 多版本并存(2026-10-28)

用户提了两件事: ① 上架和详情要能展示「安装说明」「注意事项」这类**可选**信息栏;
② **一个软件要挂两个不同的版本, 两个都有用** —— 该怎么管。

#### ① 选填信息栏

| 字段 | 存哪 | 详情里怎么显示 |
|---|---|---|
| 安装说明 `install_steps` | `software_items` | **有序列表**(一行一条) |
| 注意事项 `caveats` | `software_items` | **醒目提示块**(黄底 + ⚠) |

- 两个都是**选填**: 没填 → 详情页**这一栏整个不渲染**, 不占位、不留空壳.
- 上架表单里这两栏标着「选填 —— 填了详情页会显示…」, 让人知道填了有什么用.
- `PUT /software/{code}` 能补写 (上架时忘了写, 后面再补).

#### ② 多版本并存

原来后端**已经是**条目 1:N 版本(旧版仍可下), 但"两个版本都有用"这个场景缺三样东西:

| 能力 | 做法 | 后端 |
|---|---|---|
| **变体标签** | 给版本起个小名, 如「Windows版」「LTS版」「通用版」 | `software_versions.variant` (选填) |
| **推荐下载版本** | 手动指定该下哪个, 头部「⬇ 下载」跟着走 | `software_versions.is_default` |
| **单版本下架** | 只撤掉传错的那一版, 其他版本照旧能下 | `DELETE /software/{code}/versions/{version}` |

关键设计:

- **`is_default` 放在版本行上, 不放条目上** ——
  "该下哪个"天然是版本的属性; 换推荐只是把某一行的标记挪走.
  条目上的 `version` 字段是"当前版本指针"(发新版本自动切), 它回答"最新的是哪个",
  跟 is_default 回答的"该下哪个"是**两回事**.
- **推荐位必须唯一** —— 发新版本(默认接管推荐)时, 后端自动把旧版的推荐标记摘掉;
  手动设推荐时同理. 不唯一的话前端不知道该指哪.
- **发新版本时可以选「不接管推荐位」** —— 适合"LTS 版还在给老环境用"的情况.
  抽屉里那个复选框默认**勾上**(发新版=让大家下新的), 主动取消才不抢.
- **推荐版本永远不被自动清理** —— `keep_versions` 清理老版本时, 推荐的那一版豁免.
  否则悄悄把用户特意留着的版本清掉, "该下哪个"就悬空了.
- **单版本下架**: 删掉最后一个能下载的版本 → 条目一起下架(不能空着上架);
  删别的版本 → 条目照旧上架, 其余版本照旧能下.
- 详情页版本行: 变体标签(蓝色)、推荐(绿色)、⬇下载 / ⭐设为推荐 / 下架这版.
  只有一个版本时**不显示**"共 N 个版本"那句 —— 多余.

#### 这轮踩到的坑

- ⚠️ **SQLAlchemy 的 `synchronize_session` 跟 SQL 实际匹配范围不一致** ——
  发新版本时"把旧版推荐标记摘掉"那条 UPDATE, WHERE 里要排除新版本自己.
  但新版本刚 `session.add()` 还没 flush 时 `ver.id` 是 None → 拼出来的 `id != NULL`
  在 SQL 里**恒不成立**, 而 ORM 的 'evaluate' 策略又在 Python 侧按同样条件改了内存对象 ——
  两边不一致, 推荐标记直接错乱.
  **修法**: 先 `await session.flush()` 拿到 `ver.id`, 再执行 UPDATE,
  并加 `.execution_options(synchronize_session=False)` (手工改比 ORM 猜得准).
- ⚠️ **MySQL 的 TEXT 列不能带 DEFAULT** ——
  `ALTER TABLE ... ADD COLUMN install_steps TEXT NOT NULL DEFAULT ''` 报
  `BLOB, TEXT, GEOMETRY or JSON column can't have a default value`.
  **修法**: 先加成可空列 → `UPDATE` 回填空串 → 再 `MODIFY ... NOT NULL`.
- ⚠️ **alembic revision id ≤ 32 字符** —— 0026 最初叫 `0026_sw_install_notes_and_variants`
  (35 字符), DDL 全执行完了但版本号写不进 `alembic_version.version_num`.
  改名 + `alembic stamp` 补上 (DDL 是非事务的, 列已经建好了, 别重复跑).
- ⚠️ **组件测试里抽屉靠 `watch(modelValue)` 触发读取** ——
  一上来就传 `modelValue: true` 的话 watch 不会 fire (没变化), 详情永远是空的.
  必须先挂成 `false`, 再 `setProps({ modelValue: true })`.
- ⚠️ **vi.mock 的工厂函数会被提升** —— mock 里引用模块级的 `const getSoftware`
  会 TDZ 报错, 必须用 `vi.hoisted`.
- **e2e 里 el-checkbox 不能只点 `input`** —— Element Plus 把真正的 input 藏起来了,
  要点 `.el-checkbox__label`.


所以 `scripts/migrate_categories.py` 里必须有**逐资产**的映射表 `TARGET_CATEGORY`
(13 个存量资产一个不漏), 不能只按旧分类查表。查表兜底 `FALLBACK_BY_OLD` 只是给
"以后新传进来的"用的退路, 命中了会**大声报出来**。

#### 迁移要改**四处**, 少一处就自相矛盾

```
① GitLab 工作区的目录   assets/{kind}/{slug}/{code}   ← slug 换了要搬目录
② 每个资产的 manifest.json  category + git_path + 文案
③ index.json          分类与文案都在索引里
④ DB 的 assets 表      category / git_path / 文案字段
```

只改 DB 的话: 同步器下一次就从远端把老分类拉回来 —— **GitLab 是真源, DB 只是镜像**。
脚本 `python3 scripts/migrate_categories.py --apply` 一次做完并 commit+push, 退出前回读
DB / index.json / manifest 三处核对。

#### ⚠️ 两个坑(下次改脚本必看)

1. **`git mv` 之后再 `git add -A -- <旧路径>` 会直接失败**:
   `fatal: pathspec 'assets/skills/diagnose/x' did not match any files`
   (旧路径已经被 `git mv` 从索引里删了, 既不在索引也不在工作区).
   但 `git commit -- <旧路径> <新路径>` 是**好的** —— 提交的临时索引是
   "HEAD + pathspec 对应的工作区内容", 旧路径的删除记录在索引里会一起进提交.
   → 所以 `git_sync.sync_paths_blocking` 加了 `commit_paths` 参数:
   **`paths` 给还能 add 的(新路径+index.json), `commit_paths` 给要进提交的(新+旧+index.json)**.
   漏了旧路径, 远端会**同时留着新旧两份目录**.

2. **迁移方案要按**工作区 manifest** 算, 不能按 DB 算**:
   真源是 GitLab(工作区是它的本地检出), DB 只是镜像.
   按 DB 算的话, "DB 已迁 / 工作区未迁"(或反过来)时会算出**空计划** ——
   脚本啥也不干, 看着像"没活儿", 其实根本没迁完.

#### 分类别名必须**链式**解析

#### 顺手修掉的两个真 bug(截图验收时撞出来的)

#### ② 新增「🔌 体检存储目录」—— 换根目录**不会自动搬文件**

这是本轮最实的一个功能。改 `software.storage_path` 只是**改指针**,
老文件还躺在旧目录里 —— 不体检的话, 管理员改完路径照样上传成功、下次下载 404,
而且完全不知道为什么。

新增端点 `POST /api/v1/settings/test/software_storage`(admin only):

```
ok        → 可写 · 软件库已占 0.0 GB / 磁盘剩余 200.9 GB · 文件都在  路径 …
warn      → 目录不存在: <root> —— 建出来或者换个已经存在的路径
warn      → 目录存在但不可写: <root> —— 权限不对 (容器里通常是没挂卷)
```

`detail` 里给 `root` / `exists` / `writable` / `used_bytes`(软件库自身) /
`free_bytes`(整盘剩余) / `missing_count` / `missing[]` /
**`source`**(`setting` | `env` | `default` —— 告诉管理员这个路径**是哪来的**)。

`source` 特别重要: 裸机模式下路径来自环境变量 `SOFTWARE_STORAGE_PATH`,
DB 里改不动它; 不说清来源, 管理员在设置页改了却"没生效"会以为功能坏了。

> ⚠️ **为什么不复用 `/software/path-check`**: 那个接口返回的是**软件库领域**结构
> (missing 列表带 code/version), 设置页要的是**能不能用**的一句话结论。
> 两个用途、两套受众, 别混。

#### ⚠️ 踩过的坑: `used_bytes` 有**两个**,含义不同

```
software_store.used_bytes(root)   → 软件库目录**自己**占多少   ← 用这个
software_store.usage_info()["used_bytes"] → 整块磁盘的已用 (shutil.disk_usage)
```

拿错的话设置页会显示「**软件库占了 725GB**」—— 那是一整块盘。
已在 `usage_info()` 的 docstring 里写死警告, 端点里也留了注释。

   第三层 `<ul>` 是 flex 子项, 宽度被压到 0, 结果「🧩 插件·技能·连接」这类长标签
   被挤成**竖排**(一个字一行)。修法: 含子项的 `li` 改用 **grid**

2. **`border-left: 3px solid var(--primary-grad)` 整条边框会消失** ——
   `--primary-grad` 是 `linear-gradient()`, `border-color` 不吃 gradient。
   要用 `var(--primary)`。
3. **placeholder 里别留 `**`**: placeholder 是从 description 首句截断来的,

4. **改大段模板别用行号**: 这次先用行号切, 结果前面一次小改动(目录加了三层)
   让所有行号**整体错位**, 拼出一个重复的 section + 孤儿的 `grp` 引用,
   `vue-tsc` 报了一堆 `Property 'grp' does not exist`。

### ⑲ 审核总开关: 一个开关管上架 + 下架 (2026-10-28 晚)

用户要求: 「上架更新和下架审核可以在设置中加个开关, 默认开启, 关闭后上传者可以免审核」。

#### 拍板的两个决定

1. **一个开关管两件事** —— 复用已有的 `marketplace.review.enabled`, **不新增第二个设置项**。
   它在设置页「🗂️ 能力墙 → 📦 资产 → 🧩 插件·技能·连接」分组下, 本来就是个 bool 开关。
2. **免审下架 = 自助下架并保留文件**(进 `unpublished` 态),
   **不给作者「直接删除」的权限** —— 删除不可逆, 而市场是共享的(别人可能正在用)。
   要彻底删除仍然只能管理员来(申请制那条路, 或 admin-only 的 `DELETE /{code}`)。

#### 开关关掉之后的行为

| | 开关开 (默认) | 开关关 (免审) |
|---|---|---|
| 上传 / 更新 | 进「待审核」, 管理员通过才在市场可见 | **直接上架**, 不用等 |
| 下架 | **申请制**: 作者申请 → 管理员确认 → 资产被**彻底删除** | **自助下架**: 立刻从货架消失, **文件保留**, 随时可「重新上架」 |
| 彻底删除 | 只能管理员 | 只能管理员(**不变**) |

#### 实现要点

- **状态机新增动作 `take_down`**(`app/core/market_state.py`):
  `((PUBLISHED,), UNPUBLISHED, "author")`, 审计标签「自助下架 (免审核, 文件保留)」。
  这条路径以前**根本不存在** —— 状态机定义了 `unpublished` 态、前端也有徽标和「重新上架」按钮,
  但没有端点能进这个态(见 §9 第 7 条)。
- **`POST /{code}/unpublish` 加免审分支**: 读 `_setting_bool("marketplace.review.enabled", True)`,
  为假 → `_set_publish_state(publish_status="unpublished", action="take_down")` + 发 `unpublish` 通知;
  为真 → 原来的申请制(`unpublish_pending`)。`confirm_code` 校验在两个分支**之前**, 绕不过去。
- **`GET /assets/config` 暴露 `review_enabled`**(**生效值**, 不是 schema 默认值) → 前端据此改按钮文案与确认框。
- **通知**: 事件 key 仍是 `unpublish`(开关映射靠 key, 不能乱换), 只用 `title_override`
  换标题「📦 资产已下架 (文件保留)」—— 免审下架**不是**彻底删除, 标题别再写 🗑。

#### ⚠️ 踩过的坑

1. **Vue Boolean prop 的「缺省强转成 false」**:
   `reviewEnabled?: boolean` 不显式给 `default: undefined` 的话, 父组件没传时
   `props.reviewEnabled` 是 `false` 而不是 `undefined` ——
   「取不到开关 → 保守按开着处理」会反过来变成「取不到 → 按免审处理」, **方向正好反了**
   (拿不准时该多走一次审核, 而不是少走)。
   修法: `withDefaults(defineProps<...>(), { reviewEnabled: undefined })`。
2. **改开关语义会连带打穿一批单测**: 以前有 17 处单测拿
   `marketplace.review.enabled="false"` 当「让上架免审」的捷径。
   现在这个开关关掉后**下架也变自助**, 申请制那条路根本测不到 →
   全部改成「开着 + 代管理员 approve 一下」来拿在架资产。
   同时把 `_publish_asset`(只上传) 和 `_published_asset`(上传 + 代通过) 拆开 ——
   要 pending 资产的用例不能代通过。
3. **单测里断言「文件是否保留」要查工作区目录**, 不能查远端裸库 ——
   单测没有后台 worker, 远端根本没被推, 「文件还在」和「文件被删了」是**同一个假象**。
4. **e2e 必须用非管理员账号测**: `marketplace.review.admin_self_approve`(默认开)
   让管理员自己的上传免审核 —— 拿 admin 测, 开关开开关都是 `published`, 根本测不出效果。
   (e2e 里要建发布者账号 + 加 `marketplace.publisher_usernames` 白名单, 结束必须还原+删号。)
5. **e2e 上传走 `package` 字段, 不是 `files`**: `files` 是**多文件文本**上传,
   塞 zip 进去后端报「不是 UTF-8 文本」; 而且包名必须与资产 code 一致(后端 `_assert_naming` 会拦)。
6. **市场页默认停在「插件」tab**: 技能资产根本不渲染 ——
   e2e 找不到卡片不是数据的问题, 是 tab 没切过去。
7. **返回字段别叫 `reviewed`**: 两条路返回时都「还没被审核过」, 这个字段等于没信息。
   改成 `needs_review`(申请制 `true` / 自助 `false`)。
8. **ElMessageBox 是纯文本, 不渲染 Markdown**: 确认框里写 `**立刻生效**` 会把星号**原样显示出来**
   (设置页的 description 才是走 Markdown 的)。弹窗里一律用「」。
9. **`_ACTION_COMMIT_TEXT` 别漏**: 新动作不在这个表里, git commit 文案会落成兜底的「更新资产」——
   提交历史里就看不出这次到底是上架还是下架。`take_down` → 「自助下架」。

### ⑳ 软件标识自动生成 + 文件名校验 + 「下架删目录」全流程修复 (2026-10-28 晚)

用户提了两个问题:

1. **「code 不要用户来填写, 自动根据软件英文名称来维护」** + 「上架的软件包名称必须是英文数字和标准字符, 上架时校验」。
2. **「我全下架了多个版本, 但重新设置过的根目录下的这个目录没删除」** (`software/dify-web-entrypoint2`) —— 「看看这个流程的坑还有哪些」。

#### 问题 ①: 软件标识(code)改成自动派生 + 文件名当场校验

**拍的板**: 「软件英文名称」= **上传的软件包文件名**(去掉扩展名)。理由: 中文「软件名」生成不出 code;
用户自己那次的 code (`dify-web-entrypoint2`) 本来就取自 `dify-web-entrypoint.sh`;
而且「软件包的名称必须是英文数字」这句话指向的也是文件名。→ **不新增输入框**, code 选完文件后**只读自动生成**。

| | 改前 | 改后 |
|---|---|---|
| code 谁定 | 用户手填 | **后端按文件名派生** (`code_from_file_name`) |
| code 撞名 | 409 冲突 | **自动加序号** (`base2` / `base3`, 最多 999 次) |
| 文件名不合规 | `sanitize_filename` **静默改名** | **当场 422 拒绝** (中文/空格/括号/以点开头) |
| 前端 | 可编辑输入框 | **只读** + 「自动」标签, 选文件时实时显示 |

- 派生规则(前后端**一字不差**): 去扩展名 → 转小写 → 非法字符换 `-` → 合并连续 `-` → 去掉首尾 `-._` → 截 64 位 → 不足 2 位补齐。
- 文件名规则 `FILE_NAME_RE = ^[A-Za-z0-9][A-Za-z0-9._-]{0,199}$`(以字母/数字开头)。
- **为什么不再 sanitize**: 静默改名用户不知道, 下载回来名字对不上更麻烦。`sanitize_filename` 降级成**兜底**。
- 空 `file_name` 仍然**允许**(兜底 `{code}-{version}.bin`) —— 不破坏既有 API 契约(老调用方只传元数据)。
- 前端新增 `validateFileName` / `codeFromFileName`(`frontend_web/src/views/Software/softwareForm.ts`), 有 12 条新单测锁住。

#### 问题 ②: 「下架删目录」的三个坑 + 修法

**根因 A(用户报的)**: 逐个「下架版本」只删 `<root>/<code>/<version>/`,
上层 `<root>/<code>/` 的**空壳目录没人清理** → 用户看到目录还在。

**根因 B(更大的坑)**: 落库的 `file_path` 是**相对路径**(`code/version/file_name`),
而所有删除/下载逻辑都用**当前** root 拼它 → 管理员改了 `software.storage_path` 之后,
「当前根 + 相对路径」找不到老文件了 —— **文件还在旧根躺着, 但下载 404、删除删不掉**, 成了删不掉的孤儿。
实测现场: 设置项根 = `TestMate/software`, 环境变量根 = `deploy/native/runtime/data/software`(文件实际在这), 默认根 = `data/software` —— **三个根并存**。

**根因 C**: 软删条目(`delete_software`)按设计**保留文件**, 只有 `purge` 才真删; 而 `purge` 也只删当前 root 下的。

**修法(不引入 alembic 迁移)**:

- **多根候选** `software_store.candidate_roots(当前根, 历史根)`:
  顺序 = 设置项根 → `software.storage_path_history` → 环境变量根 → 默认根(去重)。
  ③④ 天然覆盖「改设置项之前」的存放位置, 所以绝大多数情况不用额外维护。
- **查找**: `locate_under` / `locate_version_dir` / `locate_item_dir` —— 依次在候选根里找。
  下载端点改用 `locate_under` → **换根后老文件照样能下**。
- **删除**: `remove_version_dir_anywhere` / `remove_item_dir_anywhere` —— **所有**候选根里的同名目录都删
  (改过好几次根目录时同一路径可能在两个根都存在, 只删找到的第一个不够)。
- **空壳清理**: 删完版本顺手 `remove_item_dir_if_empty(root, code)` → 这就是用户报的那个目录。
- **换根时记历史**: `PUT /settings/software.storage_path` 触发 `_remember_old_storage_root` →
  旧根归一成绝对路径追加进新设置项 `software.storage_path_history`(最多 20 个)。
- **体检端点把「缺」拆成两类**(设置页「体检存储目录」+ `GET /software/path-check`):
  · **missing** —— 当前根没有, 但**别的根**里找到了(文件没丢, 下载/删除会自动去找)
  · **lost** —— 所有候选根都没有(真丢了)
  · 另外报告**孤儿目录**(根下有目录但 DB 里没这个 code)。
- 软删(`delete_software`)**仍然保留文件**(设计如此), 彻底删除走 `purge` —— `purge` 现在会清所有候选根。

#### ⚠️ 踩过的坑

1. **钩子在提交之后才读旧值 → 历史根永远记不上**:
   `update_setting` 里先 `commit()` 再调 `_remember_old_storage_root`, 函数内部回读数据库拿到的**已经是新值** →
   `old == new` 直接 return。修法: **写入新值之前**把旧值抓出来传进去(已加单测 `test_changing_storage_root_remembers_old_root`)。
2. **`select(...)` 忘了 `.scalars()`**: `await session.execute(select(SoftwareItem.code)).all()` 拿到的是 **coroutine**,
   报 `AttributeError: 'coroutine' object has no attribute 'all'` —— 两处(software.py / settings.py)都踩了。
3. **图标全局唯一(另一条并行会话加的规则)**: 新写的「撞名加序号」用例没给唯一图标 →
   先撞图标 409。**造新用例时记得图标也要换**。
4. **前端 code 只读后提示要改口径**: 用户改不了 code, 所以校验失败时的提示要说「**换个软件包文件名**」,
   而不是「只能用小写字母…」(他改不了, 只会懵)。
5. **别用行号切 Vue 模板**: 行号会整体错位 —— 用 `src.index('...')` 内容定位。

#### 实测验证(只跑「下架删目录」这条流程, 真实实例走平台 API)

```
切到旧根上架 tm-verify-b (code 自动生成) → 文件落在旧根
切回新根 → storage_path_history 自动记下旧根 ✅
换根后下载 → HTTP 200 / 11 字节 / 内容一致 ✅        ← 根因 B
下架版本 → 旧根里 tm-verify-b/1.0.0 与空壳 tm-verify-b/ 全删 ✅ ← 根因 A+B
当前根对照组 → 空壳目录也删 ✅
purge 4 个条目 → 遗留的 dify-web-entrypoint / dify-web-entrypoint2 目录消失 ✅
收尾体检 → missing=1(xx 在旧根, 没丢) lost=0 orphan=0
```

顺手清掉了用户遗留的两个空壳条目(`dify-web-entrypoint` / `dify-web-entrypoint2`, 都是今天测试留下的软删条目);
`xx` 条目(`xx/1.0.0/mineru.json`)按约定**没动**。

### ㉑ 「下架这版」成功却报「软件 xxx 不存在」(2026-10-28 晚)

用户截图: 点「下架这版」→ 绿色提示「版本 1.0.0 已下架」✓, 紧接着两条红色「软件 dify-web-entrypoint 不存在」。

#### 根因

后端 `delete_version` 里有一条**设计**: 删掉**最后一个**能下载的版本时, 条目不能空着上架,
所以会连带把条目软删(`publish_status="hidden"` + `deleted_at=utcnow()`)。
→ 这之后 `GET /software/{code}` 必然 404。

前端不知道这件事, 下架成功后照旧 `await load()` 刷新详情 → 404 → 弹红错;
`emit('changed')` 又让父组件刷新 `refreshKey`, watch 再 `load()` 一次 → **弹两条**。
也就是说: **操作是成功的, 但界面在报失败**。

#### 修法(前端为主, 后端补一个信号)

- **后端**: `DELETE /{code}/versions/{version}` 的返回体加 `item_unpublished`(条目是否被连带下架)
  和 `remaining_versions` —— 审计里本来就有这个字段, 现在正式返回给前端。
- **前端**:
  · `item_unpublished` 为真 → 成功提示改成「版本 x 已下架 · 这是最后一个版本, 软件已一并下架」,
    **关抽屉 + 刷新列表, 不再查详情**(查了必然 404);
  · `load()` 遇到 **404 → 静默关抽屉**, 不弹红错(兜住所有路径, 比如父组件 refreshKey 触发的二次加载);
  · 「下架这版」的确认框在**只有一个可下载版本**时改口径:
    「这是**最后一个**可下载版本 —— 下架后这个软件会**一起从软件库里消失**」;
  · 「下架软件」(`purge`) 的顺序改成**先关抽屉再刷新列表** —— 反过来的话父组件刷新会在抽屉还开着时查一次详情 → 404。

#### 实测(真实 Chrome)

造一个只有一个版本的软件 → 打开详情 → 点「下架这版」→ 确认:

```
提示: ["版本 1.0.0 已下架 · 这是最后一个版本, 软件已一并下架"]   ← 只有绿色, 没有红色
抽屉已关闭 ✅   列表里条目已消失 ✅   页面 JS 错误: 无 ✅
```

单测: 后端 2 条(返回体字段)、前端 3 条(关抽屉 / 不报错 / 404 静默)。

### ㉓ 通知流程整改: 审核类通知合并 + 管理员待审入口 (2026-10-29)

用户反馈: 「**其他人上架了资产, 上架审核不会在上方通知审核, 下架貌似会?**」

#### 先说结论: 钉钉那条**发出去了**, 漏的是**站内提示**

查 `asset_notifications` 回执表, 上架审核的通知确实发了
(`id=1997 · review · dml-weekly-report · status=sent`), `notify_on_review=True`、
审核群 webhook 也配了。**真缺陷在站内提示条**:

| 提示条 | 以前有没有 |
|---|---|
| 🗑 你的 N 个资产在等下架确认 (作者视角) | 有 |
| 🗑 N 个下架申请等确认 (管理员视角) | 有 |
| 📋 N 个资产在等上架审核 (管理员视角) | **没有** |

根因: 后端 `awaiting_review_count` **早就算好并下发了**, 前端**根本没用它** ——
全前端只出现在 `api/assets.ts` 的类型定义里。管理员只能扫卡片上的 📋 徽标。

顺带查出的另外两个缺陷: 审核类通知**不 @ 任何人**(`_EVENT_AT["review"] = {at_all: False}`),
正文**没有操作入口**(`link` 为空) —— 收到的人不知道该去哪审。

#### 改了什么

**① 站内待审入口 (前端)**

- 市场页顶部新增管理员提示条「📋 有 N 个资产在等上架审核 —— 通过后才出现在市场里」,
  点「只看这些」直接筛出待审列表;
- 首页待办新增「📋 N 个资产等你审核 (别人提交的)」, 点进去带 `?status=pending`;
- 市场页读 `?status=pending` 直达待审视图 (钉钉通知里的「去审核台」链接也走这个);
- ⚠️ 数量取 `awaiting_review_count - my_pending_count` —— **扣掉自己那份**,
  免得跟「你的 N 个」报同一个数;
- ⚠️ `all-pending` 筛选走**后端** `status=pending`(后端对管理员/审核人放行全部待审),
  前端再按「是不是我的」筛一遍会把别人传的资产全筛掉, 那就白点了。

**② 审核类通知的窗口合并 (后端)**

十几个人同时上架 = 十几条消息把审核群刷屏。改成:

- **首条照常发**(带完整详情 —— 管理员第一时间知道有人上传了);
- 窗口内的其余**攒起来**, 窗口末发**一条**汇总「📋 另有资产在等上架审核 · 另有 N 个」;
- 窗口默认 60 秒, 设置项 `dingtalk.aggregate_window_seconds` 可调, **设 0 = 恢复一个资产一条**;
- 汇总正文里每个资产**占一行**(`- 名字 (类型 · 版本 · 操作人 · 说明)`), 不然只剩一个数字还得自己去翻。

⚠️ **只合并审核类**(`review` / `unpublish_request`): 它们是「要人去做一件事」,
管理员的动作是「打开审核台看全部待办」。市场群那几类
(`publish`/`update`/`unpublish`/`reject`/`delete`) 是「资产已经变了」的**事实通告且 @所有人**,
**不合并** —— 合并会让人漏看谁上架了什么。

⚠️ **按事件分组**: 上架审核和下架申请分开汇总, 混一起会让人看不懂。

⚠️ **状态存 DB**(`asset_notifications.status` 新增 `aggregated` / `summary_sent` / `aggregated_sent`),
不存内存 —— 进程重启不能把攒着的通知弄丢。**不需要数据库迁移**(status 是 String)。

⚠️ **必须有后台聚合 worker**(`start_aggregate_worker`, 每 10 秒扫一次):
窗口到期后没人再触发事件, 攒着的通知就永远发不出去。

⚠️ **汇总失败不重复发**: 汇总发送失败时**复用**那条回执重试(不新建),
且重试 worker **跳过汇总回执** —— 两个 worker 各发一遍 = 群里收到两条一样的。

⚠️ **审核入口链接用 `marketplace.public_base_url`**(为空就不给链接, 不编造打不开的地址),
不新增设置项。

#### 顺带修的两个真 bug (e2e 逼出来的)

1. **分类 chip 的计数跟列表对不上** —— `/assets/categories` 只数 `published`,
   而列表对管理员返回**全部**状态(待审 / 待下架 / 已驳回都在列表里, 各自带徽标),
   于是 chip 写 3、点进去是 5 张卡。改成按**这个用户能看到什么**来数(跟 `GET /assets` 同一套规则),
   并支持 `?status=` 跟当前筛选一致(「只看待审」时 chip 也切口径)。
   > ⚠️ 这个 bug 以前没暴露, 是因为生产库里一直**没有别人的待审资产**;
   > 用户传了一个上去, 它就露出来了。

2. **`e2e_software.js` 的 E6 断言过期** —— 软件标识 2026-10-28 起是**自动生成**的
   (由文件名派生, readonly), 脚本还在手填「唯一标识」。已改成断言「是只读的自动字段」
   + 选完文件后自动派生出来(E12b)。

### ㉔ 全站时间差 8 小时 —— 时区契约整改 (2026-10-29)

用户拍板「只修 1」。

#### 病根

库里存的是 **naive UTC**(`datetime.utcnow()`, MySQL 的 DATETIME 没时区概念),
但 API **原样把它吐出去**:

```
"updated_at": "2026-10-28T16:09:01"      ← 没有时区后缀
```

JS 的 `new Date("2026-10-28T16:09:01")` 会按**浏览器本地时区**解析 ——
本机是 UTC+8 → 显示出来比真实时间**晚 8 小时**。
通知记录、审计记录、资产更新时间、"X 分钟前" **全是错的**。

⚠️ 这个约定是全项目一脉相承的 —— 后端 `review_agent_client._v2_state` 里
`ts.replace(tzinfo=timezone.utc)` 也是这么干的(把 ReviewAgent 的 naive 时间当 UTC),
所以**修前端比修 ReviewAgent 那条链更彻底**。

#### 改法: 两头都收

**① 后端 —— API 明确说「这是 UTC」(根因)**

新增 `backend_gateway/app/schemas/base.py`:

```python
class UTCModel(BaseModel):
    @field_serializer("*", when_used="json", check_fields=False)
    def _serialize_utc_datetime(self, value):
        if isinstance(value, datetime):
            return to_utc_iso(value)     # naive → 当 UTC → 带 Z
        return value
```

- 10 个带时间字段的响应模型改成继承它:
  `AgentOut` / `AssetOut` / `AssetNotificationOut` / `AssetJobOut` / `AssetAuditOut` /
  `SyncStatusOut` / `UserOut` / `SoftwareVersionOut` / `SoftwareOut` / `SettingOut`
  (`UserManageOut` / `SoftwareDetailOut` 继承上面两个, 自动带上);
- ⚠️ **只影响 JSON 输出**(`when_used='json'`)—— `model_dump()`(python 模式)
  还是 datetime 对象, **内部逻辑(DB 比较、排序)一点没动**;
- ⚠️ 通配序列化器对**所有字段**生效, 所以它只动 datetime, 别的原样返回
  (嵌套模型也自动带上 Z)。

**② 前端 —— 统一的解析助手(兜底)**

新增 `frontend_web/src/utils/format.ts` 的 `parseApiTime()`:

- **没时区后缀的一律当 UTC**(补 `Z` 再解析)—— 宁可当 UTC, 也不能当本地时间;
- 已经带 `Z` / `±HH:MM` 的原样解析;
- 顺带兜住「只有日期」和「空格分隔」两种写法。

改了 **10 处**时间显示点:

| 位置 | 原来 | 现在 |
|---|---|---|
| `utils/format.ts` `fmtIso()` | `new Date(v)` | `parseApiTime(v)` |
| `utils/format.ts` (新) `fmtDate()` | — | 按本地时区出 `YYYY-MM-DD` |
| `utils/capabilities.ts` `relativeTime()` | `new Date(iso)` | `parseApiTime(iso)` |
| `Catalog/AssetAuditDrawer.vue` `fmt()` | `new Date(iso)` | `parseApiTime(iso)` |
| `Settings/index.vue` `fmtTime()` | `new Date(iso)` | `parseApiTime(iso)` |
| `Settings/components/UserManage.vue` `fmtTime()` | `new Date(iso)` | `parseApiTime(iso)` |
| `Catalog/index.vue`「GitLab 最近对齐」 | `new Date(sync.last_sync_at)` | `fmtSyncAt()` → `parseApiTime()` |
| `Catalog/AssetCard.vue` `shortDate()` | `iso.slice(0, 10)` | `fmtDate()` |
| `Software/SoftwareCard.vue` `shortDate()` | `iso.slice(0, 10)` | `fmtDate()` |
| `Software/SoftwareDetailDrawer.vue` `shortDate()` | `iso.slice(0, 10)` | `fmtDate()` |
| `Catalog/AssetDetailDrawer.vue`「更新 …」 | `(item.updated_at \|\| '').slice(0, 10)` | `fmtDate(item.updated_at)` |

⚠️ **最后 4 处原来是「按字符串截取」** —— 显示的是 **UTC 那一天**,
跟页面上其它按本地时区显示的时间对不上 (晚上更新的资产差一天)。
截字符串的写法不认时区, 后端补了 `Z` 也救不了, 必须一起换成真解析。

⚠️ **GitLab 索引里的 `updated_at` 故意不改** —— `app/core/market_catalog.py`
把索引写成 `a.updated_at.isoformat()`(naive), 读回来是
`datetime.fromisoformat(...)`。索引内容要算 sha256 跟远端比对,
改了格式会让**所有资产都变成"远端有更新"** —— 那是假冲突, 别动。

#### 测试

- 后端新增 `tests/test_timezone_contract.py` **10 条**:
  序列化器本身 5 条(naive 当 UTC / aware 换算 / 带 Z / 不动别的字段 /
  python 模式不受影响) + 接口层 5 条(资产 / 通知回执 / 审计 / 同步状态 / 软件库
  的时间戳必须带 `Z`);
- 前端新增 `src/utils/__tests__/format.spec.ts` **15 条**:
  `parseApiTime` 的 8 种输入 + `fmtIso`/`fmtDate` 按本地时区 +
  `relativeTime` 按 UTC 算差值;
- 新脚本 `scripts/e2e_timezone.js` **3 条**: API 带 Z / 页面显示本地时间
  (拿回执的 UTC 时间换算后跟页面上显示的逐条比) / 无 JS 错误。

#### 效果(实测)

```
API   : "2026-10-28T16:49:30Z"     ← UTC, 语义明确
页面  : "2026/10/29 00:49:30"       ← 本地 (UTC+8), 之前显示的是 10/28 16:49
卡片  : "2026-10-29"                ← 本地日期, 之前是 2026-10-28
```

### ㉕ 知识库: 普通登录用户也能上传 / 下载文档 (2026-10-29)

用户要求:「先分析当前知识库用的 ragflow 的哪种类型的接口…再参考对应文档, 实现新增功能,
新增支持上传文档(参考具体的接口, 看看怎么实现)、下载文档(如有)等扩展功能;
目的就是上登录用户也可以上传知识库内容, **但是不能删除**」

#### ① 接口类型判定: 走 **HTTP API**, 不是 Python SDK

| 判据 | 结论 |
|---|---|
| `backend_gateway/app/core/ragflow_client.py` | 全文用 `httpx` 手写 HTTP 调用, **一行 SDK 都没有** |
| `requirements*.txt` | **没装** `ragflow` SDK; 全仓 `grep "from ragflow import"` = 0 处 |
| 配置 | 存在 DB `system_settings`(`ragflow.base_url` / `ragflow.api_key`), **不在 env 里** |
| 服务形态 | docker 容器 `ragflow-ragflow-cpu-1`, 镜像 `ragflow-local:arm64emu-fix`(基于 RAGFlow **v0.26.1**), `18080→80` |

所以按 `https://ragflow.io/docs/http_api_reference` 做就对了, **不引入 SDK**
(HTTP API 已覆盖上传/下载/解析/删除全套, 引 SDK 只是多一层依赖)。

#### ② 新增的三个接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `POST` | `/api/v1/kb/datasets/{id}/documents` | **tester 及以上** | multipart 上传, 字段名 `file`(多个同名字段=多个文件) |
| `GET` | `/api/v1/kb/datasets/{id}/documents/{doc}/download` | **所有登录用户** | 下载**原始文件**(字节流, 不是 JSON) |
| `GET` | `/api/v1/kb/audits` | 所有登录用户 | 操作审计(谁在什么时候传了什么) |

⚠️ **删除端点一行没动**, 仍然只有 admin 能删(`DELETE /api/v1/kb/datasets/{id}/documents`)。
理由: 上传进的是**共享**知识库 —— 能删就意味着能删别人的东西。

#### ③ 权限分层(user 拍板)

| 角色 | 看 | 下载 | 上传 | 删除 |
|---|---|---|---|---|
| viewer | ✅ | ✅ | ❌ | ❌ |
| tester | ✅ | ✅ | ✅ | ❌ |
| admin | ✅ | ✅ | ✅ | ✅ |

上传限制(user 拍板): **单文件 20MB / 单次最多 5 个**。
- 数量超了 → 422; 单文件超了 → **413**(分块读+边读边限, 不把超大文件整个吃进内存);
- 前端再先挡一道, 别让用户白等上传完才报错。

#### ④ 三个真踩到的坑(都是跑起来才发现的)

**① multipart 的字段名必须等于参数名**
FastAPI 是**拿参数名去表单里取值的**(`form.getlist(参数名)`), 字段名对不上就变成
「没传文件」422。最初写的是 `files: list[UploadFile] = File(...)` + 前端 `append('file', f)`
→ 14 条单测挂了 9 条, 全报 `{"type":"missing","loc":["body","files"]}`。
marketplace 那条上传接口没事, 是因为它的字段名和参数名都叫 `package`。
→ 改成参数名也叫 `file`。

**② `Content-Disposition` 是 latin-1 的 —— 中文文件名塞进去整个下载 500**
starlette 编码头值用 latin-1, `filename="知识库上传验证.txt"` 直接
`UnicodeEncodeError` → 500。规矩:
- `filename="xxx"` → **纯 ASCII 兜底名**;
- `filename*=UTF-8''xxx` → RFC 5987, 真名(浏览器优先用这个)。

**③ 「手动分块」数据集的解析器只支持 pdf/docx**
`协议文档` 数据集的 `chunk_method=manual`, RAGFlow 的 `rag/app/manual.py:295`
对非 pdf/docx 直接 `NotImplementedError("file type not supported yet")` → 文档卡在 FAIL。
→ 上传时先看数据集的 `chunk_method`, 是 `manual` 且文件不是 pdf/docx 就**不发起解析**,
并把话说明白(返回 `warning` + 前端黄条), 别让用户以为是自己传坏了。

#### ⑤ 文件名规则: 知识库**不能**套用软件包那套

`software_store.sanitize_filename` 的规则是 `[^\w.\-] → _`(空格/括号全变下划线) ——
那是因为**软件包的文件名会落成磁盘目录名**。知识库的文件名只是 RAGFlow 里的
`location`/`name`, 不落我们的磁盘, 所以 `Management Component Transport Protocol (MCTP) Base Specification(1).pdf`
这种名字**必须原样留着** —— 用户是按原名找文件的, 静默改成 `xxx_yyy_.pdf` 谁认得出来。
→ 知识库单独一套 `_sanitize_kb_filename()`: 只挡路径分隔符(路径穿越) + 控制字符(头注入)。

#### ⑥ 为什么要新建 `kb_audits` 表

RAGFlow 记不了 TestMate 的账号 —— **所有人共用同一把 API key**, 它只知道"有个文档被上传了"。
普通用户能上传之后, 必须有一张表记「**谁**传的」。所以新建 `kb_audits`(迁移 `0027`):
数据集/文档/动作/操作人/大小/时间, 复合索引 `(dataset_id, created_at)`。
⚠️ 审计的 `error` 字段只放**真的失败** —— 「进库了但这个数据集不解析」不算失败,
塞进去前端会显示成「失败」(用户以为白传了)。

  中文名下载头 latin-1 安全、manual 数据集不解析并带警告、审计留痕(含失败也留)。

而 DeepDOC 的 OCR 模型在这个 **arm64 模拟**容器里跑一页要 **~3 分钟**
(`__ocr recognize N boxes cost 450s`), 480 页 ≈ **20 小时**。
期间这 5 篇是「在库但 0 分段」—— **搜不到任何东西**。
→ 先 `docker restart ragflow-ragflow-cpu-1` 把卡住的执行器清掉(存储都在外部容器, 重启安全),
然后给**这 5 篇文档**打上文档级覆盖 `layout_recognize=Plain Text`(不 OCR, 直接抽 PDF 文字层)
+ 关掉 `graphrag` / `raptor`(这两个要调 LLM, 极慢) → **几分钟就解析完了**。
⚠️ **数据集自己的配置没动** —— 「协议文档」仍然是 DeepDOC, 别的文档不受影响。

代价: 分段数比原来少(Plain Text 没有版面/表格切分), 表格会被拍平成文本。
想要跟原来一模一样的表格感知分段, 办法是: 清掉这 5 篇的**文档级** parser_config 覆盖
(恢复成数据集的 DeepDOC) 再重跑解析 —— 但那要 ~20 小时, 建议在机器空闲时做。

**教训**: 清理脚本**只能删自己造出来的东西** —— 按文件名精确匹配, 绝不能
「把数据集里所有 id 都删掉」。现在脚本已经改成按文件名过滤。

#### ⑨ 这块还留着的尾巴

1. **`协议文档` 是「手动分块」数据集** —— 往里传 `.txt`/`.md` 传不进去解析。
   要么把它的切片法改成「通用」, 要么就让上传功能在 manual 数据集上只收 pdf/docx
   (现在是「收下但明确提示需要管理员手动切分」)。等拍板。
2. **没有做 `type=web`(网页抓取入库)** —— 会引入 SSRF 风险(内网地址), 本轮聚焦文件上传。
3. **上传没有内容安全检查** —— 谁都能往共享知识库塞东西, 现在只有「角色 + 审计」两道,
   没有敏感词/恶意文件的拦截。

| 坑 | 调研文档说 | v0.26.1 实际 | 症状 |
|---|---|---|---|
| 字段名 | `parser_id` + `parse_type=1` | **`chunk_method`**(不带 parse_type) | `Field: <parser_id> - Message: <Extra inputs are not permitted>` → 502 |
| 通用切片的值 | `general` | **`naive`** | 文档枚举里没有 `general` |

| 响应的 `data` | 数组 | **一个对象** | 写 `data[0]` 直接 IndexError |

源码依据(容器 `ragflow-ragflow-cpu-1`):
- `api/apps/restful_apis/dataset_api.py:81` —— 建库路由
- `api/utils/validation_utils.py:503` —— `CreateDatasetReq`:
  `chunk_method` 上标了 `serialization_alias="parser_id"` —— **那只是服务内部别名**,
  对外请求字段是 `chunk_method`; `parse_type` / `pipeline_id` 这套是给「自定义解析器」用的,
  内置切片不用传
- `api/apps/services/dataset_api_service.py:87` —— service 内部 pop 的是 `parser_id`

所以链路上的值统一用 RAGFlow 自己的词: **`naive` / `manual`**。
界面显示「通用 / 手动」, 靠 `fmtChunkMethod` 映射(`naive`/`general` 都显示「通用」)。

⚠️ 另外实测过: `PUT /datasets/{id}` 只传 `description` **不会**把库名冲成空串

### ㉗ 知识库「归属 + 删除数据集」 (2026-10-29 第三轮)

**显示差 8 小时**。跟审计接口一个处理办法。

#### ④ 删除为什么这么设计

RAGFlow 的 `DELETE /api/v1/datasets` 会**逐个文档**走 `remove_document`,
连带 MinIO 里的源文件、ES 里的分段一起清掉 —— **硬删, 没有回收站, 没有任何撤销**。

所以前端做了三层防护:
1. 按钮**只给 admin** (后端也拦, tester/viewer → 403);
2. 弹框里写清楚**会删掉多少东西**(几篇文档 / 几个分段);
3. **必须原样输入库名**才能删 (对不上就只提示, 不放行)。

⚠️ `ElMessageBox` 是**纯文本**, 不渲染 Markdown —— 确认文案里不能写 `**强调**`。
⚠️ 按钮文案是「永久删除」, 不是「确定」—— 让人知道这一步不可逆。

#### ⑤ ⚠️ 真机踩的坑: `page_size=200` → `code=101`

删除路由里查库名时写的是 `list_datasets(page=1, page_size=200)`, 结果:

```
GET /api/v1/datasets?page=1&page_size=200  →  {"code": 101, "data": []}
```

**RAGFlow 的 page_size 上限是 100**, 超了它不报错, 而是返回**错误码 + 空 data** ——
看起来就像「一个库都没有」。于是删除接口回「数据集不存在」(404), 但库明明在。

⚠️ **单测测不出来**: 假 httpx / 假的 `list_datasets` 不校验 `page_size`,
一律返回全部。**只有真机才暴露**。

修法(两层):
- `ragflow_client.list_datasets` 里**夹住** `page_size`(>100 → 100), 根治;
- 调用处也改成 100, 明确。

⚠️ 另外把「取不到库信息」和「库不存在」**区分开**了: 现在前者返回 502(RAGFlow 挂了),
后者才是 404 —— 之前混在一起会给出误导性的提示。

#### ⑨ 操作记录收紧成 admin only (2026-10-29 同轮追加)

用户问「操作记录只有管理员可看?」—— 查下来发现**不是**, 当时是

用户拍板: **只有管理员能看**。已收紧:

| 位置 | 改法 |
|---|---|
| 后端 `GET /kb/audits` | 加 `user.role != UserRole.admin → 403` |
| 前端「操作记录」卡片 | `v-if="isAdmin"` —— 不渲染, 别的角色**连请求都不发** |
| 前端 `loadAudits()` | 开头 `if (!isAdmin.value) return` —— 所有调用路径都安全 |
| 前端 `watch(isAdmin)` | 角色变了(切账号/权限被改)就**清空**已加载的记录, 别留在屏幕上 |

⚠️ 跟「删除文档」「删除数据集」是同一个口径:
**破坏性和治理性的操作, 都由 admin 掌握**。

⚠️ 前端**不发请求**是有意的 —— 否则 viewer 打开页面就弹一个 403 错误提示,
用户会以为页面坏了。

真机验证: tester 403 / viewer 403 / admin 200(13 条);

### ㉘ 知识库「文档更新 + 重新解析」 (2026-10-29 第四轮)

用户原话: 「另外文档要支持更新，看看怎么实现」
追问: 「PATCH /api/v1/datasets/{dataset_id}/documents/{document_id} 这个就是更新呢，
再确认下有没得这个接口」

#### ① 用户拍板(两个决策点)

| 问题 | 拍板 | 理由 |
|---|---|---|
| 旧版本怎么处理 | **直接替换, 旧版删除** | 不留历史版本; 审计表里留一条 `update` 记录, 但旧文件本身找不回来 |
| 更新权限 | **tester 及以上** | 跟「上传文档」同一档 —— 能往共享库加东西的人, 也能把自己那篇换掉 |

#### ② ⚠️ 核心结论: RAGFlow 的文档是**不可变**的

从容器源码确认(`ragflow/api/apps/restful_apis/document_api.py`, v0.26.1):

```
PATCH /api/v1/datasets/{dataset_id}/documents/{document_id}
  能改的只有: name / parser_config / chunk_method / enabled / meta_fields
  换不了文件内容 —— 压根没有"替换内容"的接口
```

| 改哪个字段 | RAGFlow 实际做什么 |
|---|---|
| `name` | 只改名字, **不动已有分段**; 但**扩展名不许改**(`The extension of file can't be changed`), 且**同库内不许重名** |
| `parser_config` | 直接覆盖, **不触发重解析** |
| `chunk_method` | 跟当前不同才动 → `reset_document_for_reparse`(清分段 + 重置进度) |
| `enabled` | 启用/禁用 |

⚠️ **multipart 上传不读 `name` 表单字段**(只有 `type=web`/`type=empty` 分支读) ——
文档名只能来自上传的文件名。

#### ③ 所以「更新」是网关自己拼的**四步**

```
① 传新文件    → RAGFlow 新建一条记录 (同名会自动加 "(1)" 后缀)
② 删旧文档    → 硬删 (旧版的分段 / MinIO 源文件一起没了)
③ PATCH 新文档 → 名字改回目标名
④ 迁移归属 + 启动解析
```

⚠️ **先传后删** —— 中途任何一步失败, 旧文档都还在, 用户的数据不会丢。
反过来先删后传, 传失败就两头空了。

⚠️ **文档 id 会变** —— RAGFlow 里新文档是另一条记录。
所以前端更新完必须**丢掉缓存重新拉列表**, 不然拿着旧 id 继续操作会 404。

#### ④ 变更的接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| PUT | `/api/v1/kb/datasets/{dataset_id}/documents/{document_id}` | **tester 及以上** | 换新文件替换内容(新增, multipart 字段名 `file`) |
| POST | `/api/v1/kb/datasets/{dataset_id}/documents/{document_id}/reparse` | **tester 及以上** | 重新解析(新增, 内容不变) |

`ragflow_client` 新增两个函数: `update_document()` / `parse_documents()`。

#### ⑤ 归属怎么跟着挪

RAGFlow 里「更新」= 删旧建新 → 文档 id 变了, 而 `kb_document_meta` 的主键就是
`document_id` —— 不跟着挪的话新文档会显示「上传者 —」(用户会觉得"我刚传的怎么没人")。

所以更新后: 删旧行 + 按新 id 建一行, 上传者记成**这次更新的人**。
语义跟上传一致 —— 「**当前这一版**是谁传的」; 最初是谁传的在审计表里有完整历史。

#### ⑥ ⚠️ 真机踩到的坑

1. **同名上传会自动加 `(1)` 后缀** —— `duplicate_name()`
   (`ragflow/api/db/services/__init__.py:45`), 后缀插在扩展名**前**
   (`a.txt` → `a(1).txt`)。所以更新完必须 PATCH 改回原名, 否则用户看到「a(1).txt」,
   以为多了一篇。**改名要在删旧之后** —— 同库不许重名。
2. **扩展名不许改** —— 用户传了别的类型的文件, RAGFlow 的改名会拒。
   这时候那不是「更新内容」而是「加一篇」, 所以网关**提前 422 拦掉**, 别做半成品。
3. **文档名上限是 255 *字节***(不是字符) —— `api/constants.py: FILE_NAME_LEN_LIMIT = 255`。
   中文一个字 3 字节, 按字符裁会超。新增 `_fit_kb_name_bytes()` 按字节裁,
   **而且必须保住扩展名**(裁没了改名请求就废了)。
4. **`ParserConfig` 是 `extra="forbid"` 的严格模型** —— 所以**不搬**旧文档的
   `parser_config`。实机核对过: 文档级跟数据集级**完全一致**, 搬过去没意义;
   硬搬反而容易因为 RAGFlow 版本字段变动而整个 PATCH 失败。
   新文档天然继承**数据集**的切片方式。
5. **删文档是同步的** —— `remove_document()` 第一步就是删 DB 行,
   所以删完立刻改名不会撞重名。(删**数据集**才是异步的。)
6. **manual 数据集不硬发解析** —— RAGFlow 的 manual 解析器只认 pdf/docx
   (`rag/app/manual.py`), 传 .txt 硬发解析必然 FAIL。沿用上传那套规则:
   不发解析 + 明确 warning。

#### ⑦ 前端

- 文档子表操作列加 **「更新」「重解析」**(tester 及以上才有; viewer 是只读角色)
- 「更新」抽屉: 写清楚**旧版本会被永久删除** + 只能换内容不能换类型
- 更新完**丢掉缓存重新拉列表**(id 变了)
- 有 warning 时**弹警告而不是成功**, 而且抽屉**不关** —— 话得让用户看完
- 「重解析」先弹确认框, 写清楚会清掉多少分段
- 操作记录新增两个动作标签: `update`→「更新」、`reparse`→「重解析」

### ㉙ 知识库「按文件名搜文档」 (2026-10-29 第五轮)

#### ① RAGFlow 的 keywords 真实语义

从容器源码确认(`api/db/services/document_service.py:135`):

```python
docs.where((cls.model.kb_id == kb_id), (fn.LOWER(cls.model.name).contains(keywords.lower())))
```

| 特性 | 结论 |
|---|---|
| 匹配字段 | **只有文件名** (`name`) —— **不搜文档内容** |
| 大小写 | **不敏感** (`LOWER(...)` 两边都转) |
| 方式 | **子串**匹配 —— 搜「指南」能命中「n8n 部署完整指南.md」 |
| 范围 | **单个数据集内** —— 搜全部库得**逐个库**查 |

⚠️ 「不搜内容」这件事**页面上必须写清楚** —— 否则用户搜"验收"搜不到内容,
会以为文档不存在。

#### ② 变更的接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/kb/documents/search?keywords=xxx` | 所有登录用户 | **跨数据集**按文件名搜 (新增) |

- `keywords` 空 → 直接返回空,**不去查 RAGFlow**(白跑一轮)
- `dataset_id` 可选 —— 给了就只搜那一个库

⚠️ 权限是**所有登录用户** —— 搜索是**只读**操作, 跟「看数据集」「下载文档」同一档。

#### ③ 实现要点

- **并发查各个库** (`asyncio.gather`) —— 4 个库串行等就是 4 倍延迟
- 一个库搜失败**不能拖垮整个搜索**(记 warning, 继续)
- 每个库最多翻 5 页(单页 RAGFlow 上限 100), 总数超 `limit`(默认 200)会标 `truncated`
- 前端**防抖 400ms** —— 每敲一个字就发一轮「每个库一次请求」, 库多了会把 RAGFlow 打爆
- 离开页面**清掉防抖定时器** —— 不然它在后台照样触发

#### ④ 前端

⚠️ **搜索框就放在「数据集」那个卡片里** —— 用户明确要求「不用单独增加搜索 box」。

- 搜索框放在「数据集」卡片的**标题行工具栏最左边**(它是"查找", 不是"操作"),
  跟 `+新建数据集` / `⬆上传文档` / `↻刷新` 并排
- 搜出来的结果**直接落在同一个卡片里**(标题行下面、数据集表格上面),
  不用跳来跳去 —— 独立再开一个「文档搜索」卡片反而把页面切碎了
- 结果表: 文档名 / 所属数据集 / 大小 / 分段 / 解析 / 上传者 / 操作
- 操作直接复用现有的 `分段 / 下载 / 更新 / 重解析` —— **搜到就能接着干活**
- 搜到后可以直接点文档名打开详情
- 「只搜文件名, 不搜内容」这句话**一直挂在搜索框旁边**(不只在结果区) ——
  不然用户搜内容搜不到, 会以为文档不存在

⚠️ 跨库搜索结果里**没有完整的 KbDataset 对象**(只有 `dataset_id`), 所以那几个
操作函数的第一个参数从 `KbDataset` 收窄成 `{ id: string }`(`DsRef`) ——
完整的 KbDataset 照样能传(结构化类型)。

⚠️ 操作必须传**所在库**的 id 而不是文档 id —— 传错了会 404。

#### ③ 建库可选解析器 + 语言 —— ⚠️ 这里有三个 RAGFlow 的坑

**坑 1: 对外字段是 `chunk_method`, 不是 `parser_id`.**

`parser_id` 只是 RAGFlow 服务内部的 `serialization_alias`
(`CreateDatasetReq` 里标的), 当请求字段直接传会被判
"Extra inputs are not permitted". **真机实测**:

```
POST {"parser_id": "naive"}  → code 101  Extra inputs are not permitted
POST {"chunk_method": "naive"} → code 0  ✅
```

**坑 2: 通用切片的值是 `naive`, 这版 RAGFlow 不认 `general`.**

真机实测 `POST {"chunk_method": "general"}` → code 101.
容器里 `validation_utils.py` 的合法集合:

```
{"naive", "book", "email", "laws", "manual", "one", "paper",
 "picture", "presentation", "qa", "table", "tag", "resume"}
```

⚠️ `parser_config` 里另有个 `method` 字段("light"/"general"/"ner"),
那个跟 `chunk_method` 是两回事, 别混.

**坑 3: 建库接口**不吃** `language`.**

`CreateDatasetReq` 里**根本没有** language 字段(它只是 `Knowledgebase`
**数据库模型**的列). 真机实测 `POST {"language": "Chinese"}` → code 101
Extra inputs are not permitted.

但 `UpdateDatasetReq` (**PUT** `/datasets/{id}`) **有**它. 所以网关的流程是:

```
POST /datasets   (建库, 不带 language)
PUT  /datasets/{id} {"language": "Chinese"}   (补语言)
```

⚠️ 而且 RAGFlow 建库时的**默认语言是 English**(容器 `LANG` 不是 `zh_CN`,
DB 默认值就是 English) —— 所以中文库**必须**显式补那一次 PUT, 不补就是英文库.

⚠️ 补 PUT 失败**不能**把整个建库搞失败(库已经建出来了), 但也**不能**谎报成功 ——
返回体里带 `warning`, 前端弹黄色提示. 谎报成功 = 用户以为语言设上了,

#### 根因 A: Element Plus 的悬停态是 `.is-hovering`, 不是 `:hover`

Element Plus 的下拉项**不用 CSS 伪类**, 而是用 JS 给当前项加 `.is-hovering` 类:

```css
.el-select-dropdown__item.is-hovering { background-color: var(--el-fill-color-light) }
.el-select-dropdown__item.is-selected { color: var(--el-color-primary); font-weight: 700 }
```

`--el-fill-color-light` 默认是 `#f5f7fa`(**近白**)。以前 `main.css` 只覆盖了
`:hover` 伪类, `.is-hovering` 那条**从来没被覆盖过** —— 暗色主题下就是
「白底 + 浅色字」, 选项整个看不清。**这就是用户说的「选中/悬停变白」。**

修法两条一起上(`.is-hovering` 是键盘/脚本态, `:hover` 是鼠标态, 缺一不可):

```css
.el-select-dropdown__item:hover,
.el-select-dropdown__item.is-hovering {
  background: var(--surface-sunken) !important;
  color: var(--primary) !important;
}
/* 选中项: Element 只给了 font-weight, 底色要自己定 */
.el-select-dropdown__item.is-selected {
  background: var(--primary-soft) !important;
  color: var(--primary) !important;
  font-weight: 700;
}
```

#### 根因 B: `el-option` 的 `label` 是「选中后显示的那行字」

```html
<el-option :label="p.label" :value="p.value">
  <span>{{ p.label }}</span>
  <span class="opt-desc">{{ p.desc }}</span>   <!-- 长解释只在这里显示 -->
</el-option>
```

`label` 短 → 输入框里完整; `label` 长 → 被截成「通用 —— 哪个…」。

⚠️ **`label` 同时是过滤匹配的对象** —— Element 的 `useOption` 里
   `currentLabel = props.label ?? props.value`, 下拉过滤测的是 `currentLabel`。
   所以长解释**不能**塞进 `label`, 否则「筛选」也会跟着长。

#### ⚠️ 原生 `<select>` 的 `<option>` 是个独立的老坑

`select` 元素本身的底色我们改了, 但**展开后那一列选项是 `<option>`** ——
它的底色**不继承** `select` 的 `background-color`, 浏览器按自己的默认来(白底)。
macOS 上主要靠 `tokens.css` 里的 `color-scheme: dark` 让系统弹层自动变暗,
这条规则是给其它浏览器/平台兜底的:

```css
select option {
  background-color: var(--bg-base);   /* 必须**不透明**, 不能用半透明的 --surface */
  color: var(--ink-900);
}
```

#### ⚠️ 本轮踩的坑(都是自己写出来的, 已修)

1. **`--el-checkbox-unchecked-bg-color` 这种变量名 Element 里根本不存在** ——
   实际叫 `--el-checkbox-bg-color` / `--el-checkbox-checked-icon-color`。
   更坑的是: **`el-checkbox` 压根不用额外变量** —— 它的底色走
   `--el-fill-color-blank`、边框走 `--el-border-color`、选中态走 `--el-color-primary`,
   **这三个上面已经映射过了**, 所以复选框自动就跟主题走了。
   → 写了三个不存在的变量名(死代码), 还手写了一堆 `!important` 去覆盖 —— 全删。
2. **`.el-alert { background-color: ... !important }` 会把类型色冲掉** ——
   `el-alert` 的 `effect` **默认值就是 `light`**, 实际渲染出来是
   `.el-alert.el-alert--warning.is-light`, 它自己的底色是
   `var(--el-alert-bg-color)` = `var(--el-color-warning-light-9)`。
   无脑 `!important` 盖上去 → **一条黄色告警变成灰底**, 反而更看不懂。
   → 改成 `.el-alert:not(.is-light):not(.is-dark)`。
3. **`float: right` 在 Element 的选项结构里根本不生效** —— 位置是乱的。
   而且 `max-width` + `ellipsis` 把说明**硬截断**成「…」。
   → 去掉 float/ellipsis; 说明改成 `display: inline-block` + 自己的 `max-width`,
   这样省略号**只落在说明上**, 分类名永远完整(Element 的选项行自带
   `white-space:nowrap; overflow:hidden; text-overflow:ellipsis`, 截断发生在**那一层**)。

#### ⚠️ 本轮踩的坑

1. **Element Plus 的悬停态是 `.is-hovering` 这个类, 不是 `:hover` 伪类** —— 第八轮已修,
   这轮是同一根因的延续(全站 16 个选择框都中招)。
2. **`data-theme="auto"` 是默认模式, 但组件里的暗色规则只写 `html[data-theme="dark"]`**
   —— 主题 store 会**同时**给 html 加 `.dark` class(auto + 系统暗色时也加),
   所以组件级暗色规则应该用 `html.dark`, 否则**默认模式下就是白底**。
3. **`var(--xxx)` 引用一个不存在的 token → 整条声明静默失效** ——
   `--info` / `--text-dim` 都是这样: 元素悄悄变成透明/继承父级颜色, **不报错**。
4. **全局 `select { padding: ... !important }` 会废掉各组件的 scoped 尺寸声明** ——
   实测 `.mr-state-sel` 写的 `padding: 5px 8px` 根本没生效(渲染 31px, 旁边 input 才 26px)。
   修法: 颜色/边框/箭头继续由全局锁, **尺寸**放开; 但 `padding-right` 单独用
   `!important` 锁住(自绘箭头要位置)。
5. **HTML 不允许 `<div>` 直接出现在 `<table>` 里** —— 表格包滚动容器时,
   外层表和**嵌套在它 `<td>` 里的子表**要分别包, 包错层级 Vue 编译直接报
   `Invalid end tag`。
6. **`git stash` 会把别的 worker 的在途改动一起卷走** —— 这次差点丢代码,
   恢复时用了三方合并。**并行 worker 期间禁止 `git stash`**。

### ㉞ 浮层面板整改: 抽屉/对话框/确认框「上下不协调、不是一个整体」(2026-10-30 第十轮)

**用户原话**: "所有这种抽屉的地方, 上下背景不协调, 整体都不对劲, 不是一个整体了?
改回之前全白色的?"

#### ① 根因不是「半透明」本身, 是**同一个面板里叠了多层不同的底**

第八轮(`86c1414`)给 Element Plus 补了一整套变量映射, 其中两行是:

```css
--el-bg-color: var(--surface);          /* ← 元凶 */
--el-bg-color-overlay: var(--surface);
```

`--surface` 是**半透明**的(亮色 `rgba(255,255,255,.60)`), 给页面卡片做毛玻璃没问题。
但浮层是盖在 `rgba(0,0,0,.55)` 的**遮罩**上的, 白底只要带一点 alpha,
背后的黑就透出来 → 纯白变成**灰白**, 面板看着发灰发脏。

更糟的是**同一个抽屉里叠了三层**:

| 层 | 谁画的 | 结果 |
|---|---|---|
| ① `.el-drawer` | `--el-bg-color` = 半透明 | 底色半透 |
| ② `.el-drawer__body` | `main.css` 一条全局 `!important`(注释还写着「确保 panel 不透明」, 实现却用了半透明 token) | **又叠一层** |
| ③ 暗色主题下 `header`/`body`/`message-box` | 暗色块里各自显式设背景 | **再叠一层** |

两层半透明叠出来的白 ≠ 一层半透明 → **header 比 body 暗**
→ 「上下背景不协调, 不是一个整体」。

> 第八轮之前(`5b9a38f`)根本没定义 `--el-bg-color`, 用的是 Element 默认的 `#fff` →
> 抽屉本来就是**纯白**的, 所以用户说「改回之前全白色的」。

#### ② 修法(两条, 缺一不可)

1. **只有容器画一次底色** —— `.el-drawer` / `.el-dialog` / `.el-message-box` 画 `--surface-panel`;
   内部 `header` / `body` / `content` / `btns` **一律 `transparent`**, 透出容器底色。
   这样 header 和 body 严丝合缝, 是一整块。
2. **底色走 `--surface-panel`**:
   - **亮色 = `#FFFFFF` 不透明** —— 白底只要带 alpha 就被黑遮罩透成灰白;
   - **暗色 = `rgba(15,22,40,.55)` 半透** —— 暗色下半透明叠深色背景反而更协调(用户明确要求)。

> ⚠️ EP 2.8 的实际映射(实测 `element-plus/theme-chalk/index.css`):
> `.el-drawer` → `--el-dialog-bg-color` → **`--el-bg-color`**(不是 `--el-bg-color-overlay`);
> `.el-message-box` → `--el-bg-color`; `.el-popper` / `.el-select-dropdown` / `.el-popover` / `.el-notification` → **`--el-bg-color-overlay`**。
> **两个变量都得改**, 改一个漏一个。

#### ③ 顺带必须一起改的: 浮层**内部**的填充色

面板不透明之后, 内部原来那些**半透明**的填充色(悬停底、输入框底、禁用底)
盖上去就是「白底盖白底」→ **悬停/选中根本看不出来**。

所以新增一族**不透明**的填充 token(`tokens.css`, 三套主题各一份):

| token | 亮色 | 暗色 | 用途 |
|---|---|---|---|
| `--fill-hover` | `#F1F5F9` | `rgba(30,41,59,.85)` | 悬停 / 次级底 |
| `--fill-active` | `#E2E8F0` | `rgba(39,52,73,.90)` | 选中 / 按下 |
| `--fill-disabled` | `#F8FAFC` | `rgba(14,22,38,.55)` | 禁用 |
| `--fill-blank` | `#FFFFFF` | `rgba(15,22,40,.55)` | 输入框底(= 面板色) |
| `--border-panel` | `rgba(15,23,42,.12)` | `rgba(255,255,255,.16)` | 浮层里的控件边框 |

> ⚠️ `--surface-sunken` 是**页面卡片**用的(半透明, 贴在渐变上才有毛玻璃感),
> `--fill-*` 是**浮层内部**用的(相对面板的深浅, 不带透明度)。两个不能混用。

#### ④ 顺手抓到的两个真 bug

1. **遮罩规则是非法语法, 整条被浏览器丢掉**:
   ```css
   html[data-theme="dark"] .el-overlay,
   @media (prefers-color-scheme: dark) {   /* ← 选择器列表里不能出现 @media */
     html[data-theme="auto"] .el-overlay { background-color: rgba(0,0,0,.7) !important; }
   }
   ```
   「auto + 系统暗色」那档 0.7 **一直没生效**。已拆成三条独立规则。
2. **`.el-drawer__body` 那条 `!important` 老 bug**: 注释写着「确保 panel 不透明」,
   实现却是 `background-color: var(--surface)`(半透明)—— **注释和实现反了**。
   现在 header/body 一律 `transparent`, 由容器统一画底色。

#### ⑤ 漏网之鱼: 抽屉**内部**的块「白盖白」(同一天补)

面板改成**纯白**之后又暴露出第二个问题 —— 抽屉**内部**那些用
`var(--surface)` (半透明白 `rgba(255,255,255,.60)`) 的卡片 / 版本行 / 标签 / 代码块,
盖在纯白面板上 → 合成后**还是纯白** → **底色层次全没了**, 只剩一条 6% 的淡边框。

> ⚠️ 讽刺的是: **改之前**(抽屉半透)这些块反而是有层次的 ——
>    因为块底色 0.6 叠在抽屉 0.6 上 = 0.84, 比周围亮一点点.
>    面板一变纯白, 这层差别就没了。**面板和块必须一起改。**

实测(用 `scripts/e2e_overlay_audit.js` 自动扫, 见下): **亮色下 19 个块白盖白**
(软件库抽屉 11 个: `.mini-btn` `.sec-no` `.ver-row`; 资产市场抽屉 8 个:
`.ad-install` `.ad-scope` `.ad-doc` `.tag` `code`)。
暗色下半透明叠深色, 差值只有 1/255, 肉眼看不出来, 问题轻得多。

✅ **修法(零组件改动)**: 在浮层容器里把整个 `--surface` 家族**重新定义**成
「相对面板的实色」—— 组件里写 `var(--surface)` 的地方**自动**就对了:

```css
.el-drawer, .el-dialog, .el-message-box {
  --surface:        var(--panel-surface);        /* #F1F5F9  /  rgba(30,41,59,.85) */
  --surface-soft:   var(--panel-surface-soft);   /* #F8FAFC  /  rgba(30,41,59,.55) */
  --surface-sunken: var(--panel-surface-sunken); /* #E2E8F0  /  rgba(4,6,14,.90)   */
}
```

⚠️ **为什么不能直接改 `--surface` 这个 token 本身**: `--surface` 是**页面卡片**用的
(半透明贴在渐变上才有毛玻璃感), 改了就全站没有玻璃感了。
所以是**在浮层内部局部重定义**, 页面上的卡片一点没动。

审计结果: **29 → 1**。剩下的 1 个是 EP 默认按钮(白底 + 边框), 靠边框能分辨, 是正常样式。

#### ⑤ 首页「重叠在一起」—— sticky 的 top 是相对**滚动容器**的

**根因**(实测, 不是猜的): 滚动容器是 `.tm-main`(MainLayout 里 `height:100vh; overflow:hidden`, 主区自己滚),
它的顶边在**视口 y=70**(上面是 70px 高的 AppHeader)。

`position: sticky; top: 52px` 的 top 是相对**滚动容器**算的, **不是相对视口** → 真实含义是
「离 `.tm-main` 顶边 52px」= 视口 y=122。而工具条的**静态位置**只有 y=78, 远在 122 之上 →
sticky 规则把它**往下顶 44px** → 工具条底边(184)压进网格顶边(156) → **重叠 28px**,
工具条的下边框正好横穿第一排卡片的标题, 卡片图标也被切掉一半。

**实验证据**(逐个改样式量间距):

```
❌ 原始              gap=-28   ← 重叠
✅ position:static  gap=16
✅ sticky top:0      gap=16
```

**修法**: 工具条的 sticky 偏移 = **待办带的实测高度**(没有待办带就是 0), 由 `ResizeObserver` 喂进 `--strip-h`:

```css
.home-toolbar { position: sticky; top: var(--strip-h, 0px); z-index: 3; }
```

- 没有待办带 → `top: 0` → 工具条停在静态位置, 一点不压网格;
- 有待办带 → `top: 待办带高度` → 滚动时正好排在待办带**下面**, 两者不叠;
- ⚠️ 高度用 ResizeObserver **实测**(待办条会换行, 写死 52 迟早再压一次);
- 待办带是 `v-if` 的, 元素换人时得**重新挂**观察 → `watch(stripEl, ...)`.

**顺带修**: 设置页 `.set-toc` 的 `top: 16px` → `top: 0`(同一个根因, 目录整体被顶下 16px 跟右边标题不齐)。

> ⚠️ **教训**: sticky 的 `top` 永远相对**最近的滚动容器**, 不是视口。
>    本项目的滚动容器是 `.tm-main`, 不是 window —— 写 `top` 前先确认滚动容器是谁。

#### ① 通知链接基地址 —— 动态获取

**取值顺序**(`app/core/dingtalk.py` 的 `_notify_base_url()`):

1. `dingtalk.notify_base_url` —— **显式配置, 优先**(用户主动配了就听用户的, 比如要发公网域名给外部人);
2. **动态推断** —— "这次请求是从哪个地址进来的"(同事打开 `http://10.0.0.5:8081`, 链接就是那个);
3. `marketplace.public_base_url` —— 市场的对外基地址(给 Qoder 装包用的);
4. 都没有 → **不带链接**(别发一个打不开的地址)。

**实现要点**:

- `app/core/dingtalk.py`: 新增 `ContextVar _request_base_url` + 进程内缓存 `_last_base_url`

- `app/main.py`: 新增 `@app.middleware("http") _capture_public_base_url` ——
  优先读 `X-Forwarded-Host` → `Host`, proto 读 `X-Forwarded-Proto` → `request.url.scheme`;
- `deploy/native/units/nginx.conf.tpl`: **3 处** location 都补 `proxy_set_header X-Forwarded-Host $http_host;`

> ⚠️ **Host 头是客户端可控的** —— 直接拼进链接能被构造成钓鱼链接。
>    所以要过 `_sanitize_host()`: 只放行字母数字、点、横线、冒号, 其余一律丢弃。
>    (nginx 自己也会拒掉非法 Host, 但后端这层是**直连 8000 端口**时的兜底。)
>    实测: `X-Forwarded-Host: evil.com/#x` → 链接里**不会出现** `evil.com`,
>    回落到"最近一次推断到的合法地址"。

> ⚠️ **后台任务没有请求上下文**(聚合汇总 worker / 重试 worker)→ 用进程内缓存 `_last_base_url` 兜底。

| 2 | **连接器 (mcp) 没得下载**, 卡片上的下载计数可以去掉 | 交互 | 连接器压根没有安装包, 下载接口直接 400 |

#### ① 下载计数为什么"不累计"—— 同步把它清零了

**根因**(`app/core/market_catalog.py`):

- `download_count` 以前**写进了 `index.json`**(索引 = "这个资产是什么"的**源状态**);
- 而 `apply_index_to_db()` 在**每次同步**时都用索引里的值**覆盖** DB 的实时计数:

  ```python
  a.download_count = max(0, int(e["download_count"]))   # 以前: 直接覆盖
  ```

- 索引里存的是**发布那一刻的快照**(绝大多数是 0), 而 `marketplace.sync.interval_seconds` 默认 **30 秒** ——
  所以**每 30 秒就把所有资产的下载计数清零一次**。用户看到的永远是 0。

**实测(改之前)**:

```
下载 ssd-log-doctor 3 次  → 计数 3
触发一次 POST /assets/sync → 计数 0     ← 被清零
```

**修法**(两处一起改):

1. `apply_index_to_db()`: **不再覆盖**, 改成**取两边的较大值** —— 计数只增不减,
   跨实例同步也不会抹掉已有的下载数; 索引里是**坏值**(字符串/浮点)时**保留原值**
   (以前是清零 —— 一条脏数据就能把下载数抹了);
2. `asset_to_index_entry()`: **索引里不再写 `download_count`** ——
   下载次数是**运行时指标**(这个部署里谁下载过), 不是"这个资产是什么"的源状态。
   放进索引就等于每次同步都拿旧快照盖掉实时计数。

#### ③ 软件库的下载 —— 排查结论: **正常**

- 下载走**短时票据**(`POST /{code}/download-ticket` → `GET /software/dl?t=...&v=...`),
  票据 10 分钟有效、绑定账号和版本;
- 条目级和版本级计数**都原子自增**(`SoftwareItem.download_count + 1` / `SoftwareVersion.download_count + 1`);

- 软件库**不进市场索引**, 所以**没有**① 那种"被同步清零"的问题。

- 版本被**彻底删除**时, 它的版本级计数一起没了(条目总数仍在) —— 合理;
- 「**覆盖已有版本**」时版本行是**复用**的(不删行), 旧文件的下载计数**保留**在新版本上
  —— 语义上是"这一版被人下过多少次", 保留比清零更符合直觉。

#### ① 状态徽标颜色统一 —— 引入**语义色调**

**根因**: `STATUS_LABELS` 里 board / platform 两种角色的 `beta` 和 `stable`
**文案都是「正常」**, 但徽标 class 按**原始 status** 生成(`st-${status}`) ——
`code-review`(board/stable) → `st-stable` 绿, `agent-market`(platform/beta) → `st-beta` 橙。
**同一句话两个颜色**。

**改法**: 新增 `statusTone(kind, status)` → `ok | warn | muted | danger`,
class 由**色调**决定, 不再由原始 status 决定:

| | draft | alpha | beta | stable | deprecated |
|---|---|---|---|---|---|
| tool | muted 规划中 | warn 内测 | warn 公测 | ok 可用 | danger 已下线 |
| board / platform | muted 未接入 | muted 未接入 | **ok 正常** | **ok 正常** | danger 已下线 |

⚠️ CSS 同样按惯例**提到全局** `styles/main.css` 一份(`.st-ok/.st-warn/.st-muted/.st-danger`),
`AppHeader.vue` / `CapabilityCard.vue` 里的 scoped 副本删掉 —— 这是**第四次**"各抄一份"了。

⚠️ **踩到一个 CSS 特异度坑**: scoped 样式编译成 `.pt-badge[data-v-x]`(0,2,0),
比全局 `.st-ok`(0,1,0)**高** —— 只删 `.st-*` 那 5 条而留着 base 规则里的
`background`/`color`, 徽标会**永远显示灰色**, 修复静默失效。
所以两个组件的 base 规则里**去掉了 `background`/`color`**, 颜色一律由全局色调类给。
⚠️ vitest 没开 `css: true`, **单测跑不出这个坑**, 只能靠编译产物核对。

#### ② ③ 筛选维度互斥 + tab 计数**恒定**

**根因(两个)**:
- 市场页: `toggleMineOnly()` 只清 `onlyMine` 不清 `category`, 分类 chip 也**不清** `mineOnly`
  → 「👤 我的」和「⭐精选」能同时高亮, 后端把 `status=mine` + `category=xxx` 一起发,
  结果既不是"我的全部"也不是"该分类的全部";
- 软件库: 「全部」tab 的 active 条件是 `category === '' && !mineOnly`, 但点「全部」**只改 category**
  → 选过「我的」之后点「全部」**点不亮**, 要再点一次「我的」才切得回去。

**改法**: 两页的「全部 / 我的 / 各分类」都收敛成**同一个维度**, 同一时刻只能亮一个
(`selectCategory()` / `selectMine()`, 内联的 `@click` 全删)。

⚠️ **计数口径是这轮的关键**: 以前 tab 上的数字用的是 `total`(**当前筛选结果数**) ——
一选「我的」, 「全部 N」也跟着变成"我的"数量 → 用户看到「全部 3 | 我的 3」,
完全不知道库里到底有多少。

后端两个列表接口各加两个字段:

| 字段 | 含义 | 受不受分类影响 |
|---|---|---|
| `all_total` | 忽略 category 的可见总数 | ❌ 不受 |
| `mine_total` | 当前用户作为作者的条数 | ❌ 不受 |

- 软件库 `SoftwareListOut`: `all_total` = 默认可见性(管理员看全部 / 普通用户看"已上架+自己的"),
  **不跟 `status` 参数走** —— 所以选「👤 我的」时「全部 N」还是全库数;
- 市场页 `AssetListOut`: `all_total` = 默认可见性 + kind + q + project, 同样忽略 category 和 status。

⚠️ 市场页的 `list_assets` 原来是一条 `select(Asset)` 链式 `.where()` ——
想再算两个"恒定计数"就得把整条链抄一遍, 所以**重构成可复用的条件片段**
(`kind_conds` / `cat_conds` / `proj_conds` / `status_conds` / `author_conds` / `q_conds`),
列表 / `all_total` / `mine_total` 各自组装。

#### ④ 账号可删除(管理员也删得掉)

**新端点** `DELETE /api/v1/auth/users/{user_id}`(admin only, 204 No Content):

- 护栏① 不能删**自己**(前端也直接禁用按钮, 别让人白点一次);
- 护栏② 系统里不能一个管理员都不剩(底层护栏, 走 HTTP 其实够不到 —— 能调接口的人自己就是管理员);
- 护栏③ 删的是启用中的管理员、而剩下的人全停用 → 拦下;
- ⚠️ 删号**不删资产** —— 资产存的是**字符串用户名**, 作者名留在那儿(方便追溯),
  只是那个身份没法再登录。前端确认框必须**如实说清**这一点。

⚠️ **二次确认加强**(用户明确要求): 不是弹个框点「确定」就删 ——

## 7. 容易踩的坑(这个项目特有的)

1. **两种部署模式不能同时跑** —— 资产市场的 job 队列是进程内 `asyncio.Queue`,
   不跨进程。两个后端各有一份队列 → 同一个 job 被两个进程抢 → git `index.lock`
   冲突 / 重复推 GitLab。切模式要停 **frontend + backend 两个**;
   只停 backend 的话, 那个端口会变成「页面能开、接口全 502」的假象。
2. **Docker 模式与裸机模式的库是各的** —— 换模式不会自动带数据过去,
   要搬: `mysqldump` → `tmctl.sh local db import <dump.sql>`。
3. **改 `deploy/native/.env` 的端口后要重跑 install** —— 运行时的配置由
   `backend.env` / `nginx.conf` 派生, 只改 `.env` 不生效。
4. **改前端代码必须重建** —— 裸机模式的 bundle 是 `deploy/native/runtime/frontend`
   (`npm run build` + 拷过去), Docker 模式则要 `--build` 重建镜像。
5. **用户可见文案里不许出现「智能体」「知识库存」「Dify」** —— 主词统一是「能力」。
6. **死路菜单项比没有更糟** —— 点了没用的项比不提供更伤。
7. **前端错误提示不许把 axios 原始报文甩给用户** —— 一律走 `utils/httpError.ts`。
8. **`tmctl.sh` 的选项解析**: `local` / `launchd` 后面第一个词才是命令, 全局选项
   写在命令后面也能认(这条修在 `feature/native-zero-container` 上, 已合并)。
9. **launchd 的服务停不掉, 只能卸载** —— `RunAtLoad + KeepAlive` 的单元,
   `launchctl bootout` 之外没法"暂停": 一停它就被拉回来。
   要切回 Docker 模式 → `tmctl.sh launchd uninstall`(开机自启也一并没了)。
10. **容器模式停掉后, 后端单测的 Redis 探针会失败** —— 测试环境的 `REDIS_HOST`
    默认是容器名 `redis`, 本机解析不了 → `/health/ready` 返 503。
    跑 readiness 相关的测试时要把 Redis 探针一并 mock 掉
    (见 `tests/test_market_health_signal.py` 的 `_patch_deps`)。
