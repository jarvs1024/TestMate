# 能力墙重构 — 从「智能体广场」到「能力工作台」

> 2026-10-25 · 面向「TestMate 是 SSD 测试组的测试伙伴」这一定位，重新定义前端的信息架构。
> 目标读者：前端 / 后端 / 测试组同事。
>
> ⚠️ **2026-10-27 部分内容已过时** —— 角色名「底座」改成「**资产**」、资产组排到最上面、
> 工具组只留「环境运维」、「AI 资产市场」改名「**插件·技能·连接**」、新增「**软件库**」。
> 本文保留 10-25 当时的设计推理（为什么收敛成三种角色）; 当期现状看
> [本轮变更](2026-10-27-capability-wall-rearrange.md)。
>
> 第一版把能力分成四种「形态」（工具/看板/目录/知识），
> 第二版收敛为三种「角色」（工具/看板/底座）—— 理由见 §2。

## 一、为什么要改

当前首页叫「智能体广场」，卡片数据来自 `GET /api/v1/agents`，`agents` 表是**智能体注册表**。但这张表里真正能跑的只有一半：

| code | 名字 | 实际是什么 | route |
|---|---|---|---|
| `log-analysis` | 日志分析 | **工具**（填参数 → 出结果） | 默认走运行页 |
| `env-ops` | 环境运维 | 工具（规划中） | 同上 |
| `test-plan-gen` | 测试方案生成 | 工具（规划中） | 同上 |
| `testcase-gen` | 文本用例生成 | 工具（规划中） | 同上 |
| `code-review` | 代码检视 | **看板**（只读指标） | `page:code-review` |
| `agent-market` | AI 资产市场 | **底座**（技能沉淀） | `page:market` |
| `kb-inventory` | 知识库 | **底座**（RAG 语料） | `page:kb-manage` |

于是三个结构性问题：

1. **卡片按实现形态建模（agent），用户按使用意图感知（跑一个活 / 看一个盘 / 取一份料）。** 两套坐标系不一致，用户每次都要重新判断"这个是不是智能体"。
2. **卡片元信息是假的。** 所有卡片统一显示 `🔧 引擎 / 📊 调用次数 / 🕐 最近调用` —— 对看板和底座全是假信息（资产市场永远 0 次调用，代码检视没有引擎可言）。
3. **知识库被抬成平级分区。** 用户看到的是"两个功能区"，不是"一堆能力"。

**根因**：卡片缺一个表达"**这张卡在平台里扮演什么角色**"的字段。`category`（ssd-trace / ssd-spec / auto-code…）是**业务域标签**，跟角色正交，不能复用。

## 二、核心模型

### 2.1 一张卡 = 一项「能力」

> 统一主词：**能力**（用户层）。引擎层保留「智能体」（`agent.engine` = 内置 / n8n），两者各归其位。

### 2.2 三种角色（kind）

角色只回答三件事：**干活 / 看数 / 供料**。

> ⚠️ 第一版分四种「形态」（工具 / 看板 / 目录 / 知识），但「目录」「知识」都在**泄漏实现**：
> 一个说的是目录结构，一个说的是内容形态，跟用户脑子里的"这东西能干嘛"对不上。
> 事实上资产市场里三种资产的官方说明写得很清楚 ——
> 「一段可复用的方法与知识, 装进 Agent 后直接照着做」「让 Agent 连到外部服务」，
> 资产本来就是**装进 Agent 的扩展**；知识库则是 RAGFlow 的数据集/分段，是**检索语料**。
> 两者同属一类：**给上面两种能力供料的底座**。

| kind | 角色 | 徽标 | 用户在做什么 | 成员 |
|---|---|---|---|---|
| `tool` | 工具 | 🛠 | 干活：填参数 → 出结果 | 日志分析、环境运维、测试方案生成、文本用例生成 |
| `board` | 看板 | 📊 | 看数：只读指标，不改数据 | 代码检视 |
| `platform` | 底座 | 🧱 | 供料：技能沉淀 + RAG 语料 | AI 资产市场、知识库 |

**细分信息没丢** —— 底座里的两类靠 **category** 区分（`ai-market` / `ssd-kb`），
卡片副行分别是「🧱 底座 · AI 资产」和「🧱 底座 · 知识库」。

### 2.3 CTA 由每张卡自带

同一角色下的卡**动法不同**：底座里资产市场是「浏览技能包」，知识库是「检索语料」。
所以 CTA 不能由角色决定 —— 每张卡自带 `cta` 字段（admin 以后加卡也能自己写按钮词），
前端在 `cta` 为空时回落到角色默认词。

| 卡 | 角色 | CTA |
|---|---|---|
| 日志分析 | 工具 | 开始使用 |
| 代码检视 | 看板 | 查看看板 |
| AI 资产市场 | 底座 | 浏览技能包 |
| 知识库 | 底座 | 检索语料 |

### 2.4 状态语义按角色换词

`status` 字段（draft/alpha/beta/stable/deprecated）保留在后端，但**卡片上的徽标按角色换词** —— 对看板和底座说"Beta / 稳定"没有决策价值：

| 角色 | 徽标词 |
|---|---|
| 工具 | 规划中 / 内测 / 公测 / 可用 / 已下线 |
| 看板 | 未接入 / 正常 / 已下线 |
| 底座 | 未接入 / 正常 / 已下线 |

### 2.5 知识库的两层理解

- **第一层（已落地）**：知识库从侧栏顶级项降级为**一张卡**，与其他能力同列，点进去仍是现有的知识库工作区（数据集 / 文档 / 分段 / 检索 / 对话）。
- **第二层（后续可选）**：每张能力卡可挂**专属数据集**（`dataset_id` 绑定 `capability_code`），让「日志分析」只检索指定知识源。需要后端加绑定表，本次不做。

### 3.1 四个区块的职责

1. **待办带（sticky 置顶）**——首页真正的职责是"告诉我今天该看什么"，不是"列功能"。只放**需要你行动**的事：资产待审 / 同步失败 / 知识库未接入 / 能力刚上线。每条可点击直达对应能力。
   **平台技术状态（RAGFlow / ReviewAgent）不上首页**——那是侧栏"服务状态"的活。
2. **角色筛选 + 搜索**——主筛选维度是**角色**（全部 / 工具 / 看板 / 底座，带计数），状态筛选降级为工具条右侧下拉。
3. **能力网格**——3 列大卡（沿用现有 `.card` 视觉语言），**可用在前、规划中沉底**；组内按 精选 → 最近使用。
4. **最近使用**——需要一张跨角色的 usage 表（现有 `call_count` 只覆盖工具型）。本次不做。

### 3.2 卡片解剖

```
┌──────────────────────────────┐
│ [🛠]  日志分析        [公测] │   图标 + 名称 + 角色徽标 + 状态徽标
│       工具 · Trace 诊断       │   角色在前，域标签在后（版本号下沉详情页）
│                               │
│ 贴 kernel ring buffer…        │   摘要 1–2 行
│                               │
│ #日志 #诊断 #Demo             │   域标签
│ ────────────────────────────  │
│ 🔧 平台内置 · 🕐 3 小时前       │   按角色变化的 meta 行
│ 开始使用 ›                    │   CTA（卡片自带）
└──────────────────────────────┘
```

meta 行按角色取**真实数据**（不是静态文案）：

| 角色 | 数据来源 | 显示 |
|---|---|---|
| 工具 | 能力记录自带 | 引擎 · 最近使用 |
| 看板 | `GET /review-agent/metrics/overview` | 数据源 · 覆盖 MR 数 · 建议数 |
| 底座（资产市场） | `GET /assets` | 资产数 |
| 底座（知识库） | `GET /kb/datasets` | 数据集 · 文档 · 分段 |

取数失败一律降级为兜底文案，**不阻塞卡片渲染**，也**不弹全局错误**（`silent: true`）。

## 四、侧栏 = 能力导航器

侧栏从「页面导航」改成「能力导航器」，并按**四层**排版（2026-10-25 第三轮加）：

```
能力 ─────────────────      ← ① 区块标题：先说清楚这一块是什么
┌────────────────────┐
│ ▦ 全部能力      7   │      ← ② 总览入口（卡片化，权重高于单个分组）
└────────────────────┘
🛠 工具            4         ← ③ 角色组标题（加粗深色）+ 组下细分隔线
│ ──────────────────
   🪵 日志分析               ← ④ 能力条目：缩进在组标题之下
   🔧 环境运维      规划中
📊 看板            1
│ ──────────────────
   🚀 代码检视
🧱 底座            2
│ ──────────────────
   🏪 AI 资产市场
   📚 知识库
─────────
📡 服务状态
RAGFlow    正常
ReviewAgent 正常
ReviewAgent 未配置
```

**为什么要分层**（用户反馈"全部能力导航无层次感"）：改之前侧栏是**平铺**的——「全部能力」/ 组标题 / 条目三者视觉权重一样，组标题是 10.5px 灰色 uppercase（中文 uppercase 没意义，几乎看不见），条目跟组标题左边界相同（看不出父子关系），三组之间只有 6px 间距（糊成一坨）。用户看不出「全部能力」是**总览入口**而不是又一个分类。

排版规则：

| 层 | 处理 | 目的 |
|---|---|---|
| ① 区块标题 | 10.5px / 700 / ink-500 + 右侧细线 | 界定"这一块是能力目录" |
| ② 全部能力 | 卡片（边框 + 底色 + 右侧总数），选中时主色边框 | 总览入口的权重高于单个分组 |
| ③ 角色组标题 | 12.5px / 700 / ink-900 + 计数，**不再** uppercase | 组标题要看得见 |
| ③ 组下分隔线 | 组标题下 1px 细线 | 组标题与它的条目成一个视觉单元，三组自然分开 |
| ④ 能力条目 | 左缩进 24px，排在组标题之下 | 明确的父子关系 |
| ④ 当前项 | 浅主色底 + **左侧 2px 竖条** | 竖条是"当前位置"的经典指示，比整块边框轻 |

理由：侧栏 = 功能目录，首页 = 总览，两者**共用同一份能力数据**，不会出现"侧栏有、首页没有"的情况。知识库从此不再是平级分区，就是列表里的一张卡。

底部服务状态面板（`AppSidebar.vue` 现有实现）拆成独立组件 `ServiceStatus.vue`，职责单一。

## 五、详情页统一外壳

四个详情页共用 `components/CapabilityShell.vue`——**一行身份条**：

```
← 返回工作台 │ [🛠] 日志分析 v0.1.0  工具 · Trace 诊断  ● 公测      [可选动作区]
```

**外壳不自己取数**，由页面把自己已知的 name/icon/kind/status/version/category 传进来（避免每个详情页多打一次接口）。

### 描述只说一次（2026-10-25 第四轮）

原来外壳底部还有一行 `summary`，但页头（`AppHeader`）已经有 lede——两行说的是同一句话的两种写法（例：资产市场 lede「智能体的技能沉淀 —— …」vs summary「团队共享的插件 / 技能 / 连接器 —— …」），用户看着只觉得啰嗦。

现在的分工：

| 层 | 负责 | 内容 |
|---|---|---|
| 页头 `AppHeader` | **页面级** | 这是什么页面 + 一句话说明（lede） |
| 外壳 `CapabilityShell` | **能力级** | 这是哪项能力 + 什么角色 + 现在能不能用 + 能做什么操作（**没有描述行**） |
| 正文 | 内容本身 | 需要说明的地方就地写（例：工具型的 summary 放在「参数配置」卡顶部，跟着它描述的参数走） |

四个详情页一律不再往外壳传 `summary`。设置页同理：正文里那行灰字 lede 已并进页头 lede（「平台配置 · RAGFlow / ReviewAgent / 用户管理 · 改完立刻生效, 不需重启」）。

顺带把外壳从两行压成一行（padding `10px 14px` → `8px 12px`，margin-bottom `14px` → `10px`），正文多出约 40px。

## 六、匿名策略

首页**匿名开放只读**：看得见能力清单与角色，**点进去需要登录**。

- 后端 `GET /agents` 用 `get_optional_user`（无 token / 无效 token → anonymous 占位用户）。
- 前端 axios 拦截器把首页路径纳入 `publicRead` 路由：登录用户用 user token，匿名用户用 `VITE_ANONYMOUS_READ_TOKEN`。
- 匿名点非公开能力 → 跳 `/login?redirect=<目标>`；`code-review` 保持匿名可看（现状不变）。

## 十三、附：登录重构（2026-10-25）

用户要求："普通用户登录用户名为邮箱，后缀可以固定为 @twsc.com.cn，登录后可以记录用户名，下次自动填写，同时支持一键免密登录（只要用户名正确即可），管理员依旧需要密码登录"。

> ⚠️ 随后又追加了一条约束（**以这一版为准**）："用户名不能是任意都能登录，需要管理员加账号才行，登录是需要鉴权的，可以在管理员的设置来设置添加账号"。
> 也就是说 —— **免的是密码，不是身份**：账号必须先存在（管理员建过）才能登录。详见 §十四。

### 身份模型

| | 身份 | 登录方式 |
|---|---|---|
| 普通用户 | 公司邮箱 `xxx@twsc.com.cn`（域名固定） | **免密** —— 只填用户名 |
| 管理员 | 账号名（不含 `@`，如 `admin`） | **必须密码** |

域名固定在 `config.py` 的 `AUTH_EMAIL_DOMAIN`（默认 `@twsc.com.cn`）。输入框可以只填前缀，后端补后缀；填了完整邮箱就按原样用。

### 免密的含义

免密 = **不用输密码**，前提是这个账号是管理员认可并建过的（§十四）。不是"谁都知道邮箱就能进"。

### 接口

`POST /api/v1/auth/login` 的 `password` 变成可选。管理员缺密码时返回：

```json
401 { "detail": { "code": "password_required", "message": "管理员账号需要密码" } }
```

前端据此展开密码框——**不能**改成笼统的"用户名或密码错误"，否则用户会一直以为自己密码错了，而实际是"这账号压根不需要密码"。

### 前端

登录页默认**只有一个输入框**（真一键）：填完用户名回车即登录。密码框按需出现（后端说 `password_required`，或用户点「用密码登录」）。

记住两样东西（localStorage）：上次用的用户名（自动填好）、"这个账号要密码"（下次直接把密码框摆出来，管理员不用多点一次）。

顺带删掉了原来硬编码在表单里的默认账号密码。

### 数据面

| 表 / 列 | 处理 |
|---|---|
| `users.username` | 非 admin 的账号 → 邮箱形式（迁移 `0020`） |
| `assets.author` / `asset_audits.actor_name` | 同步改成邮箱形式（迁移 `0020`） |
| 白名单 `publisher_usernames` / `reviewer_usernames` | **不迁移**，改成容错匹配：填短名或全邮箱都命中 |
| 资产作者比对（列表 + 详情） | 同样容错 —— 免得某个环境漏跑迁移时"我的资产"整片消失 |

身份口径统一放在 `backend_gateway/app/core/identity.py`（登录、建号、白名单、作者比对共用一份实现），免得各写各的迟早对不上。

## 十四、账号管理（2026-10-25）

用户追加："用户名不能是任意都能登录，需要管理员加账号才行，登录是需要鉴权的，可以在管理员的设置来设置添加账号"。

### 核心变化：身份是鉴权的第一道闸

```
改前:  填个公司邮箱 → 自动开通 → 免密进    ← 知道同事邮箱 = 进了他的号
改后:  填个公司邮箱 → 库里没这个号 → 401   ← 账号必须管理员先建过
```

**免的是密码，不是身份。** 「免密」只保留在"管理员认可这个号"的前提下。

原来的 `AUTH_AUTO_PROVISION` 开关随之删除 —— 自动开通这条路整个封死，不留一个"打开就能变回旧行为"的开关（配置项留着就是死路）。

### 账号的两种登录方式由建号时决定

| 建号时 | `password_required` | 登录 |
|---|---|---|
| 密码留空 | `false` | 免密，只填用户名 |
| 填了密码 | `true` | 必须输密码 |

管理员账号一律必须密码（角色是 admin 就一定 `password_required`，建号时不给密码直接 422 —— 建出来也登不进去）。

免密账号的 `password_hash` 仍存**随机哈希**（不是空串）：免得哪天有人加个"空密码也算对"的判断就把它放行了。

### 数据面

迁移 `0021_user_account_control`：

| 列 | 含义 | 存量默认值 |
|---|---|---|
| `users.is_active` | 账号能不能用 | 全部 `1` |
| `users.password_required` | 登录是否必须输密码 | admin 角色 `1`，其余 `0` |

**停用而不是删号**：账号名下的资产归属还在，删号会把那些资产变成无主。

### 接口（全部 admin only）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/auth/users` | 账号列表 |
| `POST` | `/api/v1/auth/users` | 建号 |
| `PATCH` | `/api/v1/auth/users/{id}` | 停用/启用、改角色、重置密码、切换要不要密码 |

原来的 `POST /api/v1/auth/register` 下线（没有任何调用方，换成语义更准的 `/users` 集合）。

用户名口径：普通用户 = 公司邮箱（填短名自动补后缀，填别的域名 422）；管理员 = 不含 `@` 的账号名（原样存，不补域名）。

### 三条护栏（防止管理员把自己锁在门外）

1. 不能停用**当前登录**的账号；
2. 不能改**当前登录**账号自己的角色；
3. 不能停用/降级**最后一个**管理员 —— 否则这个系统再没人能管账号了。

另有两条不变式：

- `password_required = true` ⟹ 这个账号有**可用**的密码（免密账号想改成"必须密码"却不给新密码 → 422）；
- 升级为管理员必须设密码（免密账号不能直接升 → 422）。

### 前端

设置页新增顶级区块「👥 用户管理」（**仅 admin 可见**，非 admin 连左侧目录项都看不到）：

- **建号表单**：用户名（普通用户带 `@twsc.com.cn` 固定后缀；选「管理员」时后缀消失——账号名不带 `@`）+ 角色 + 密码（可留空 = 免密）。
- **账号列表**：用户名 / 角色 / 登录方式（免密 vs 需密码）/ 状态；行内可改角色、重置密码、停用/启用。

登录页文案同步改成"账号需管理员提前开通"，后端回的 `account_not_found` / `account_disabled` 结构化错误直接透传给用户（不再退化成笼统的"登录失败"）。

回归测试见 `backend_gateway/tests/test_login.py`（21 条）+ `backend_gateway/tests/test_user_admin.py`（31 条）+ `frontend_web/src/views/Settings/components/__tests__/UserManage.spec.ts`（12 条）+ `frontend_web/src/views/Login/__tests__/index.spec.ts`（14 条）。

## 十六、发布权限改为「角色 + 白名单」双通路（2026-10-25 夜）

用户反馈：资产市场上传被拒，报「不在发布者白名单内, 联系管理员开通」——但当事人是**测试工程**（tester 角色）。

### 根因

线上 `marketplace.publisher_usernames` 与 `publisher_ids` **都是空的**，而原来的 `can_publish` 只有三条通路：admin、白名单 ID、白名单用户名。于是**除 admin 外谁都发不了布**——连天天要往市场里沉淀插件/技能/连接器的测试工程角色也被挡住。

报错文案只说「不在白名单内」，让人以为是配置漏了；其实模型本身就没给角色留位置。

### 改法

新增设置 `marketplace.publisher_roles`（逗号分隔，默认 `tester`），`can_publish` 变成三条通路：

| 通路 | 来源 | 说明 |
|---|---|---|
| ① admin | 角色 | 恒可发布，与任何配置无关 |
| ② 角色 | `marketplace.publisher_roles`，默认 `tester` | **测试工程默认就能上传/更新** |
| ③ 白名单 | `publisher_ids` / `publisher_usernames` | 给角色不在列表里的人开的**额外**口子 |

设置页里 `publisher_ids` / `publisher_usernames` 的描述同步改成「**额外**允许发布…」，并说明与角色口径是并集关系。

**没有**改成「tester 无条件可发」的硬编码：留一个可配的角色列表，管理员想收紧时把 `publisher_roles` 清空就退回「只看白名单」的老行为。

403 提示同步改成说清两条规则：

```
当前角色「viewer」没有发布权限 —— 可发布角色: tester; 或让管理员把你的用户名加进发布者白名单
```

### 不受影响的部分

- **能不能改别人的资产** 仍然只看「作者本人或管理员」（`can_modify`）—— 发布权放宽不等于可以覆盖别人的内容。
- **上架审核** 流程不变：默认 `marketplace.review.enabled=true`，tester 上传后进「待审核」，管理员通过才在市场可见。

回归测试见 `backend_gateway/tests/test_publisher_whitelist.py`（新增 6 条角色口径用例 + 改写 3 条旧断言）。

## 十七、设置页「🤖 智能体」→「🗂️ 能力墙」（2026-10-26）

用户反馈：「设置中还是智能体，改成能力墙」。

### 为什么必须改

能力墙重构（§一～§十一）把首页、侧栏、能力卡片全部改成了「能力」，唯独**设置页**的顶级分组还挂着「🤖 智能体」——同一个功能在两个页面两个名字，用户来回找。§七 原本留了一条边界「设置页是 admin 技术后台，保留智能体口径」，这次按用户要求推翻。

### 改法

| 位置 | 改前 | 改后 |
|---|---|---|
| 设置页分组标题 | 🤖 智能体 | **🗂️ 能力墙** |
| 左侧目录条目 | 🤖 智能体 | **🗂️ 能力墙** |
| 内部 id | `sec-agents` | **`sec-capability`**（section 的 `v-if` / `:id` / `onPickTop` 三处一起改） |
| 底座角色 hint | 供料 —— 智能体的技能沉淀 + RAG 语料 | 供料 —— **能力**的技能沉淀 + RAG 语料 |
| 市场页 lede | 智能体的技能沉淀 —— … | **能力**的技能沉淀 —— … |
| 后端 `agents.py` AI 资产市场卡 summary | 智能体的技能沉淀: … | **能力**的技能沉淀: …（**这条会渲染在能力墙卡片上**） |
| 后端 `settings.py` `CATEGORY_LABELS` | 🤖 智能体 | 🗂️ 能力墙 |

**图标选 🗂️ 而不是 🧱**：🧱 已经是「底座」这个能力角色的专用图标（能力卡片 / 侧栏分组头在用），同一个字形表示两件事会让人懵。

### 内部标识符

`sec-agents` → `sec-capability` 一并改掉。只在本文件内有 3 处引用（section 的 `v-if`、`:id`、`onPickTop` 判断），无测试依赖、无外部链接，改动零风险——留着旧 id 反而会让人以为这个分组还是当年那套「智能体业务」配置（Dify 下线后它早就是空壳了）。

### 防回退测试

名字改了不代表以后不会再冒出来。补 5 条断言，都打在**用户可见**的地方：

- 前端 `frontend_web/src/views/Settings/__tests__/capabilityWallNaming.spec.ts`（3 条）：标题是「🗂️ 能力墙」、目录 id/label/icon 对、旧 id `sec-agents` 消失、**渲染出去的代码里没有「智能体」**。
  否定断言打在「剥掉注释后的文本」上——注释里提历史（说明以前叫什么、为什么改）是允许的，拿原始源码断言会误伤。
- 后端 `backend_gateway/tests/test_capabilities.py`（2 条）：能力卡的 `name` / `summary` / `cta` / `use_when` / `not_for` 不许出现「智能体」；设置页分类标签同理。
